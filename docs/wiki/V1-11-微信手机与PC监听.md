# 微信手机与 PC 监听

这套方案把微信收款消息转发给 MPAY，用来确认原订单是否到账。安卓手机用户按本页“安卓 SmsForwarder 配置”操作；PC 方案另有工具和消息格式要求，不是安装普通电脑版微信就能直接使用。

插件编码为 `wxpay_receipt`，支付方式为 `wxpay`，日常通过后台选择名称即可，不需要手填这些编码。

## 准备与通道参数

准备本人有权使用的微信收款码、能持续收到到账消息的设备，以及可从设备访问的 MPAY 站点（HTTP 或 HTTPS）。先按[新增通道](V1-06-收款通道与支付方式.md)创建微信通道。

收款材料、金额/备注模式、有效期和偏移含义见[插件配置约定](V1-07-插件管理与配置约定.md)。再填写：

| 字段 | 怎么填 |
| --- | --- |
| 通知密钥 | 6～32 个字符，建议 16～32 位随机文本；MPAY 与工具保持一致，不使用应用 KEY 或管理员密码 |
| 通知时间容差 | 默认 30 秒，范围 5～30；比较请求时间与接收时间，设备和服务器需自动校时 |

保存并启用后，在通道详情取得通知地址。示例：`https://pay.example.com/api/pay/13/notify`，其中 `13` 是**通道 ID**，不是插件配置 ID、PID 或订单号。

## 安卓 SmsForwarder 配置

工具应安装在实际接收微信收款通知的手机上，允许通知读取、自启动及后台运行。具体权限页面依手机系统而异。

先在 MPAY 新建微信通道，选择“微信手机/PC 收款监听”。没有确认通知内容包含备注时保持“按金额识别”，收款材料使用自己的微信收款码；通知密钥按[生成说明](V1-07-插件管理与配置约定.md#生成手机通知密钥)准备后复制。保存后按[通道通知地址说明](V1-06-收款通道与支付方式.md#保存后复制通道通知地址)复制通知地址。

从 [SmsForwarder 官方项目](https://github.com/pppscn/SmsForwarder)进入其发布页获取工具，记录实际安装版本。下面按字段名称说明，具体界面随版本变化；不要从聊天附件或不明下载站获取代填密钥的工具。

| 在手机工具中找到 | 设置成什么 |
| --- | --- |
| 发送通道类型 | Webhook |
| 请求方式 | POST |
| Server / WebServer | 当前微信通道的完整通知地址，HTTP 或 HTTPS 均可 |
| Secret | 与 MPAY 当前微信通道相同的通知密钥 |
| webParams / 请求参数 | 留空，使用工具的默认表单 |
| 成功响应关键字（若有） | `200` |
| 转发规则类型 | 应用通知，来源限制为微信 |
| 规则的自定义消息模板 | 复制下方完整 JSON 一行 |

1. 在“发送通道”新增 Webhook，选择 POST。
2. Server 填通道详情提供的完整通知地址，Secret 填同一通知密钥。
3. 成功响应为 HTTP 200，正文为纯文本 **`200`**；有响应关键字设置时填写 `200`。
4. 新增“应用通知”转发规则，选择微信对应 Webhook，开启自定义模板：

```json
{"title":"{{TITLE}}","msg":"{{MSG}}"}
```

上面是写入 `content` 的模板，**不是整条 HTTP JSON 请求体**。工具最终应发送 `application/x-www-form-urlencoded` 的四字段表单，详见下节。

容易混淆的地方是 Webhook 的请求参数和规则的消息模板。对于遵循官方默认行为的 SmsForwarder，Webhook 使用 POST、填写 Server 和 Secret，`webParams` 留空，让工具生成默认表单；上面的 JSON 放到应用通知规则的自定义消息模板。不要把只有 title/msg 的模板替代整个请求，它缺少通知所需的 from/content/timestamp/sign。字段行为以 [SmsForwarder 官方 Webhook 说明](https://github.com/pppscn/SmsForwarder/wiki/附录1：向webhook发送post-get-put-patch请求)为依据。

采用 V2 教程中的中文多重匹配规则时，填写：

```text
并且 是 APP包名 相等 com.tencent.mm
并且 是 通知标题 相等 微信支付
 或者 是 通知标题 相等 微信收款助手
 或者 是 通知标题 相等 微信收款商业版
```

“或者”前保留一个半角空格。这只适用于支持该规则语法及上述 Webhook 合同的客户端版本；如果版本界面不同，按相同的包名和标题条件配置，不取消来源限制。模板变量的引号、换行须由工具正确转义，最终 `content` 必须是合法 JSON。

实际解析接受上述三个标题，正文应有“到账/收款/收款到账＋金额”等收款信息；备注模式还需消息携带四位付款备注。没有确认来源包含付款备注时，先使用金额模式。

保存规则后，确认规则和发送通道都已开启。锁屏一段时间后再做一笔核对，确保后台权限没有被系统关闭；具体手机权限页面及 PC 工具界面须按你的版本操作，本页不把其他版本截图当成通用步骤。

## 开发参考：通知传输格式

使用上面的兼容工具时，下面四个字段及签名由工具生成，普通用户无需手工计算。自行开发转发器时才需要阅读本节。

| 字段 | 值 |
| --- | --- |
| `from` | 手机为 `com.tencent.mm`；来源字符串最多 256 个字符，不含控制字符，且必须属于插件允许的来源 |
| `content` | 包含 `title`、`msg` 的非空 JSON 字符串，最多 32768 字节，必须为 UTF-8 且不含 NUL |
| `timestamp` | 当前发送时间的 13 位毫秒时间戳字符串 |
| `sign` | 工具生成的 Base64 HMAC-SHA256 签名，输入最多 132 个字符；框架解析 POST 后最多再 URL 解码一次 |

签名原文为 `timestamp + "\n" + secret`，HMAC 密钥也是 `secret`。通知从框架解析的 POST 参数中读取这四个字段；不从 URL 查询参数取值，也不因伪静态内部添加路由参数而拒绝通知。额外字段不参与处理。工具按上述默认表单发送即可；自行接入也可使用四字段 JSON POST，但 timestamp 和 content 仍须为字符串，不能将 content 直接替换为嵌套对象。HTTP 与 HTTPS 使用相同的字段、签名、时间容差、发送方及模板校验。

该兼容签名不覆盖 `from/content` 正文，也不是微信官方交易签名；不要向不可信转发端泄露通知密钥。收到正文 `200` 后仍在 MPAY 原订单确认支付与商户通知状态。

## 通知应答

手机和 PC 监听共用以下应答。使用工具默认 Accept 或 `Accept: text/plain` 时返回字符串正文，不套后台 JSON；自行接入若明确发送 `Accept: application/json`，框架会按原生内容协商将字符串编码成 JSON。

| 处理结果 | HTTP 状态 | 响应正文 |
| --- | --- | --- |
| 交易确认完成，或原事件编号未变且仍通过校验的通知重复送达 | 200 | `200` |
| 签名、时间、消息格式或订单匹配等业务校验未通过 | 200 | `400：错误原因` |

正文中的 `400` 是监听协议的业务结果，不是 HTTP 状态码。HTTP 200 表示服务器已返回应答；通知工具仍须按正文是否为 `200` 判断本次通知是否处理成功。

例如 `400：来源消息认证失败`、`400：来源消息超出接收时间窗口`、`400：收款消息未定位到唯一支付单`。根据转发日志中的正文排查；不要只看 HTTP 状态。程序故障仍返回 5xx，不能视为收款成功；使用响应头 X-Request-Id 对照服务器日志。未知通道等尚未进入插件的入口错误保留其 HTTP 状态。

这是设备向 MPAY 投递收款消息的应答。MPAY 向业务网站发送付款通知时，业务网站仍应返回 `success`，两者用途不同。

## 手机重发与时间的当前限制

安卓手机消息的监听编号由通道、来源、请求 timestamp 和原始 content 共同生成，不是微信官方交易号。重复请求只有保持这些字段一致，才能沿用原事件编号；它仍须通过接收时间窗口校验。若转发工具在重发时刷新 timestamp 或改写 content，系统会生成不同编号，当前实现不能保证把它识别为同一笔历史到账。

因此，不要通过修改时间、签名或正文把历史通知重新包装成新通知。补发前先核对原订单与实际到账；超出接收窗口的历史收款，应按[人工核对流程](V1-10-商户通知与人工处理.md)处理，不能以另一笔新订单替代原订单。

当前手机适配还使用请求 timestamp 作为到账时间。通知时间容差只检查请求与服务器的偏差，不放宽原订单付款窗口，也不取消最终确认对“付款时间不能晚于服务器接收时间”的检查。设备时间快几秒时，可能通过通知时间校验后仍无法确认订单。先校准设备及服务器时钟，再核对原付款记录；签名和时效通过不证明已取得稳定的原消息编号或真实付款时间。此段只针对安卓手机路径，PC 原始消息游标的要求见下节。

## PC / wxtool

仅使用安卓手机时可跳过本节。当前资料尚未提供经过实际验证的 PC 工具版本及逐屏配置教程，下列内容是接入格式要求，需要由工具维护者核对后接入。

需要能够输出 `wxtool.officialAccount.message` 事件并按相同四字段合同投递的工具。这里描述当前接收合同，不表示任意 wxtool 版本均已验证。

- 通知来源只接受 `gh_3dfda90e39d6` 与 `gh_f0a92aa7146c` 两个已适配公众号。
- `content` 保留完整事件对象：`event`、`account.username`、`message` 和 `delivery.messageKey`。
- 消息须为 `incoming`，`source=message`，不能为 fallback；保留原始 XML、秒级 `createTime`、`sortSeq`、`localId`。
- `delivery.messageKey` 采用工具实际游标：`账号数字ID:公众号:sortSeq:createTime:localId`，不得自行换成随机字符串。
- 插件支持当前声明的赞赏、普通收款和店员消息模板，并交叉核对标题与收款金额；系统“备注”文字不等于付款人备注。

请在工具中订阅实际收款公众号，设置正确通道地址和通知密钥，保留原始结构投递。具体微信版本、工具版本及 XML 模板需按实际样本核验；缺少适配时不得通过伪造字段绕过校验。

## 验证与排查

按[第一笔收款](V1-04-完成第一笔收款.md)先建立待付订单，再付款并检查设备投递日志、通道回调日志、原订单及商户通知。发送工具的普通测试消息不等于有效到账。

| 现象 | 检查 |
| --- | --- |
| 完全没有转发 | 微信通知开关、通知读取权限、规则启用、手机后台或 PC 休眠 |
| 验签或时间失败 | 当前通道密钥、时间同步、表单编码、签名中的 `+` 是否被误转为空格 |
| 请求格式失败 | POST 中是否包含四个必填字符串字段，content 是否为有效消息 JSON 文本；按请求编号查看技术日志 |
| 未匹配订单 | 支付方式、提示金额/备注、原单有效窗口及来源通道 |
| MPAY 成功，商城未更新 | 转到[商户通知排障](V1-17-通知验签与联调排障.md)，不要重复付款 |
