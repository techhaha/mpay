# 易支付 V1 接入指南

本文面向编写接入代码的开发者。已有商城的使用者只需按[业务网站接入](V1-15-业务网站接入.md)填写地址、PID、KEY，无需手算签名或编写下单代码。

在 MPAY 后台为业务网站创建应用，取得 PID 和 KEY，按需限制通知及返回域名。新应用已自动使用默认路由；启用通道并核对可用路由后，即可发起收款请求。

请求发送至 MPAY 站点域名。以下路径均相对于站点根目录。

## 接口一览

| 路径 | 方法 | 用途 |
| --- | --- | --- |
| /submit.php | GET / POST | 页面下单，跳转收银台 |
| /mapi.php | POST | API 下单，返回收银台地址 |
| /api.php | GET / POST | 查询应用/订单 |
| /api.php?act=refund | POST | 按原订单插件申请退款 |

参数使用 UTF-8。POST 使用 `application/x-www-form-urlencoded`，不接受 JSON、数组或重复参数名。推荐使用 POST，避免在 URL 中传递查询密钥。

返回码遵循[易支付 V1 文档](https://epay.qcjy.cc/doc_old.html)，按动作区分：

| JSON 接口 | 成功 code | 未成功或异常 code |
| --- | --- | --- |
| /mapi.php | 1（订单受理） | 0 |
| /api.php 查询操作 | 1 | -1 |
| /api.php?act=refund | 0（已确认退款成功） | -1 |

`/api.php` 的失败统一使用 `-1`，包括参数解析、认证、业务拒绝、限流及程序异常；即使尚未解析 act，也不会返回可能被退款调用方误认为成功的 `0`。错误提示仍为 `msg`，HTTP 状态按原错误类型返回。

## 请求频率与失败重试

入口先按连接 IP 限流，验签或 KEY 认证成功后再检查应用额度；`submit.php` 和 `mapi.php` 共用该应用的下单额度。默认频率及配置位置见[请求频率表](V1-31-登录验证码与请求限流.md#请求频率)。

超限返回 HTTP `429`，响应头 `Retry-After` 表示至少等待多少秒；`/mapi.php` 返回 `code=0`，`/api.php` 返回 `code=-1`，提示字段均为 `msg`。接入程序应读取 HTTP 状态及等待时间，避免立即循环重试。限流不代表原订单支付或退款失败，不应因此更换外部订单号或退款号重新申请。

访问保护明确拒绝、业务尚未执行时，响应包含 `X-Request-Rejected: 1`。一般网络超时、连接中断或其他 5xx 不能据此推断未受理，应先查询原订单。限流不改变原有签名、外部单号幂等和通知验签规则。

## 下单参数

| 参数 | /submit.php | /mapi.php | 说明 |
| --- | --- | --- | --- |
| pid | 必填 | 必填 | 应用 PID，1～32 位正整数字符串 |
| out_trade_no | 必填 | 必填 | 业务网站订单号，1～64 个字符，同一应用内唯一 |
| name | 必填 | 必填 | 订单名称；保存时按 UTF-8 截取至最多 127 字节，签名仍使用提交原值 |
| money | 必填 | 必填 | 大于零的元金额字符串，最多两位小数，例如 `12.50` |
| type | 选填 | 必填 | 已启用且绑定到应用的支付方式编码；当前插件支持 `wxpay`、`alipay`。页面下单省略时由付款人在收银台选择 |
| notify_url | 必填 | 必填 | 业务网站的异步通知地址 |
| return_url | 必填 | 选填 | 付款后返回业务网站的地址 |
| clientip | 选填 | 必填 | 付款端 IPv4 或 IPv6 地址 |
| device | 页面自动识别 | 选填 | mapi 严格接受 pc、mobile、qq、wechat、alipay 或 jump，缺省 pc；submit 按浏览器 UA 识别，不以传入值覆盖 |
| param | 选填 | 选填 | 附加参数，最多 2048 字节；非空时在成功通知中返回 |
| sign | 必填 | 必填 | 32 位小写 MD5 签名 |
| sign_type | 必填 | 必填 | 固定为 `MD5` |

submit/mapi 先按原始参数验签，再组装插件动作参数。服务固定生成平级 `_submit_type=page/api` 与 `_env`，外部同名参数不能覆盖。内部 `detectedDevice` 仅表示 submit 识别出的浏览器环境；mapi 传 null，实际设备从请求的 `device` 读取，缺省或空串使用 pc，非法枚举值拒绝。mapi 请求通常来自业务服务器，不通过该请求的 UA 推断付款设备；device 只控制呈现方式，不证明真实身份。

通知及返回地址须为合法 HTTP(S) URL，最多 2048 个字符。应用允许域名留空或包含 `*` 时不限制域名；填写具体名单时按完整域名精确匹配，每行一个，不支持子域通配。通知由 MPAY 服务器发送，默认允许端口为 80 和 443，正式通知目标须通过公网地址检查。返回地址由浏览器打开，不限制其标准 URL 中的端口或 IP 网段，也不由 MPAY 服务器查询 DNS。成功回跳仍须满足订单访问凭证、付款成功及商户确认条件，并使用原订单冻结的目标和签名凭证。

## MD5 签名

1. 移除 `sign`、`sign_type` 以及值为 null 或空字符串的参数；字符串 `"0"` 保留。
2. 按参数名的 ASCII 字符串顺序升序排列。
3. 使用原始值拼接为 `key1=value1&key2=value2`，拼接时不做 URL 编码、不去除空格、不转换金额格式。
4. 在字符串末尾直接追加应用 KEY，计算小写 MD5。
5. 将结果作为 `sign`，并添加 `sign_type=MD5`，然后按表单规则编码发送。

额外提交的非空参数也参与签名。回调验签使用收到的全部参数按相同规则计算。后台“应用管理”的签名计算工具可用于核对。

PHP 示例：

```php
function epaySign(array $parameters, string $key): string
{
    unset($parameters['sign'], $parameters['sign_type']);
    $parameters = array_filter($parameters, static fn ($value) => $value !== null && $value !== '');
    ksort($parameters, SORT_STRING);
    $parts = [];
    foreach ($parameters as $name => $value) {
        $parts[] = $name . '=' . $value;
    }
    return md5(implode('&', $parts) . $key);
}
```

参数值应为字符串。签名验证后仍需检查订单号、金额、PID 和交易状态。

## 下单响应

`/submit.php` 成功后返回 HTTP 303，跳转至收银台。`/mapi.php` 成功响应示例：

```json
{
  "code": 1,
  "msg": "订单已受理",
  "trade_no": "系统支付单号",
  "payurl": "https://pay.example.com/cashier/pay?biz_no=...&token=..."
}
```

`code=1` 表示订单已受理，尚不代表付款成功。拒绝请求时返回 `code=0` 及 `msg`；程序或基础设施故障也可能返回非 2xx HTTP 状态。

同一应用重复提交相同订单号和相同业务参数时返回原订单；参数冲突时返回错误。不同应用的同名订单互不影响。请求超时后应先查询原订单，避免用新订单号重复下单。

## 订单查询

向 `/api.php` 提交当前应用的 `pid`、`key` 和 `act`。查询接口使用 KEY 认证，无需提交 MD5 签名。

| act | 附加参数 | 结果 |
| --- | --- | --- |
| order | trade_no 或 out_trade_no；同时提供时优先 trade_no | 单笔订单 |
| orders | page 默认 1，limit 默认 20，最大 50 | 本应用订单列表，保存在 data 数组 |
| query | 无；省略 act 时使用此操作 | 应用启用状态及订单统计 |
| settle | 无 | 空结算记录；MPAY 不提供平台结算 |
| refund | trade_no 或 out_trade_no、money，选填 refund_no | 调用原订单插件；具体约定见下节 |

单笔订单在外层 `code/msg` 后返回 `trade_no`、`out_trade_no`、`api_trade_no`、`type`、`pid`、`addtime`、`endtime`、`name`、`money`、`status`、`param` 和 `buyer`。列表响应为 `code/msg/data`，data 中每项使用相同订单字段，不重复包含 code/msg。其中：

- `status=1` 表示已确认支付成功，`status=0` 表示尚未确认成功。
- `money` 为下单原金额；付款识别时的金额调整不改变此字段。
- `trade_no` 在尚未选择支付方式时可为空；`api_trade_no` 只返回已记录的支付宝、微信等接口方真实交易号，没有时为空。手机/PC 监听合成的事件编号不作为平台交易号返回，也不以平台受理单号代替。
- `buyer` 为空字符串，系统不提供付款人账户信息。

查询范围仅限当前应用。停用应用或重置 KEY 后，旧凭证无法发起新查询。`act=query` 只提供应用状态及订单统计，不返回 KEY 或平台结算账户字段 type/account/username；余额固定为 `0.00`，`act=settle` 返回空列表。这是单收款主体的接入范围，MPAY 不托管资金、不提供平台结算。

## 退款申请

向 `/api.php?act=refund` 发送 POST 表单，正文提供当前应用 `pid/key`、`trade_no`（或 `out_trade_no`）和 `money`，不重复提交 URL 中的 act。`money` 为本次退款的正数元字符串，最多两位小数。只能退款本应用已支付成功的订单，累计成功/处理中/未知退款不得超过原业务金额。

退款要求实际 HTTP 方法为 POST。GET 退款请求在进入认证和退款服务前返回 HTTP 405、`Allow: POST`，JSON 为 `code=-1` 和错误说明，不认领退款或调用插件；查询接口继续支持 GET/POST。

`refund_no` 为业务网站自定的幂等号，1～64 位字母、数字、下划线或连字符。同一支付单内，同号重试返回原退款结果，金额不同则拒绝。省略时使用原支付单唯一默认请求；需要多次部分退款时，每次业务退款必须有不同的 `refund_no`，网络重试继续使用原号。

退款处理结果含 `code/msg/refund_no/trade_no/money/refund_status`。返回的 `refund_no` 是 MPAY 的 20 位内部退款号；只有已明确退款成功才返回 `code=0`，处理中、拒绝或未执行、结果未知均返回 `code=-1`。参数、认证或程序异常同样返回非零的 `code=-1` 和 `msg`，可能不含退款记录字段。

`refund_status` 独立表示内部状态，保持 0 处理中、1 成功、2 拒绝或未执行、3 结果未知；不能与协议 code 混用。`code=-1` 不证明平台一定未退款，处理中和结果未知仍保留金额占用，不能换号重复申请，也不会自动重发。

明确拒绝与结果未知的异常说明分别记录在私有技术日志 `payment.refund_rejected` 和 `payment.refund_unknown`，可按 pay_no、refund_no、plugin_code 和 request_id 排查。说明由插件/SDK 脱敏，最多 2048 个 UTF-8 字节，超长带 message_truncated 标记；不将完整报文或凭证写入日志、数据库原因码或公开响应。

读取订单快照、校验配置或初始化插件失败时，尚未进入 `refund()`，记录为状态 2，原因为“退款准备失败，尚未执行”，不占用可退额度。原退款号再次请求仍返回该失败记录；排除原因后发起新的退款申请应使用新的商户退款号。进入退款动作后发生超时、异常或无法验证返回结果，仍按结果未知保留额度，不能据此判断平台没有退款。

当前微信/支付宝手机、支付宝账单、收钱吧码牌四个监听插件没有原路退款接口，由插件返回不支持，后台订单详情可查看请求记录。通用退款入口并不承诺任何未来平台的异步结果查询；引入该类插件前须补齐平台查询/回调及结果核对。原支付成功和已发送的付款通知不会因退款改成未支付。

## 异步通知与返回页面

确认到账后，MPAY 默认向订单的 `notify_url` 发送付款结果。管理员人工确认时可以选择暂不发送异步通知，之后在后台放行；期间查询接口仍返回支付成功，但收银台须等商户有效确认后才允许返回。通知使用 GET 参数，包含：

`pid`、`trade_no`、`out_trade_no`、`type`、`name`、`money`、`trade_status=TRADE_SUCCESS`、`sign`、`sign_type=MD5`，以及下单时非空的 `param`。

通知金额为订单原金额。通知地址原有的其他查询参数会一并参与签名；与支付协议字段重名的参数以系统生成值为准。

业务网站收到通知后应验证签名、应用、订单号、金额和交易状态，幂等完成业务处理，再以 HTTP 2xx 返回小写纯文本 `success`。允许首尾空白，不应返回 HTML 或 JSON。未获得有效应答时系统会按通知策略重试，发送记录可在后台查询。

支付成功且商户通知取得有效 success 应答并落库后，有 `return_url` 自动签名回跳；无返回地址则进入默认成功页。确认超时不改变付款结果，付款者可以重新检查。浏览器跳转用于展示结果，业务网站仍应通过服务端通知或订单查询确认支付，不能仅凭访问返回页面发货。

## 凭证变更

修改应用 PID 或 KEY 后，新请求使用新值。已创建订单的通知和返回签名仍使用下单时的 PID、KEY 和目标地址。

业务网站切换凭证时，应保留核验未处理完旧订单所需的旧 KEY。重复通知应返回相同成功应答，不能重复发货或记账。
