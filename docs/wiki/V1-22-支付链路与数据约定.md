# 支付链路与数据约定

易支付认证复用本次已读取的活动凭证完成验签；旧通知和回跳仍使用原订单冻结的凭证版本。回跳入口在一个一致性事务中完成订单访问校验、首次商户 ACK 核对和签名，与收银台共用商户应答判断；人工补发失败不撤销首次 ACK。此流程只生成返回地址，不改变支付状态。

## 从下单到确认

![支付链路](assets/payment-flow.png)

1. `/submit.php` 或 `/mapi.php` 验证应用与原始签名，再规范化业务参数。
2. `PayOrderService` 按应用和外部订单号幂等建立业务单，冻结 PID、KEY 版本和通知/返回目标。
3. `PayOrderAttemptService` 在建单事务中选路并固定支付单、通道与配置版本；已有尝试复用原记录，不重新选通道。
4. 指定支付方式的下单请求或收银台准备请求在事务提交后由 `PayOrderChannelDispatchService` 创建插件实例、`init` 并调用 `pay()`；明确拒绝与结果未知分别处理。
5. 插件返回公开的 presentation 参数，服务核对通用结构后保存订单快照；前端按注册组件展示普通扫码或支付宝入口。出现二维码不推进成功。
6. 手机/PC 经 HTTP 插件认证解析；主动采集按订单驱动，每账号每轮查询最新最多 200 条、不翻页，再整批调用插件 `matchReceipts()`。
7. 回调服务校验证据与订单归属；生命周期在事务中保存最终流水、恢复原金额、更新订单并建立通知责任。
8. `payment:work` 在事务外发送商户通知，按租约回写尝试与结果；业务网站自己完成验签和幂等履约。
9. 收银台取得首次有效商户 ACK 后才允许回跳或显示完成页；无通知地址的普通订单无需等待外部 ACK。轻量查询与展示注册见[收银台页面与扩展](V1-30-收银台页面与扩展.md)。

## 后台指定通道测试

后台 `POST /adminapi/configuration/channel-test` 接受 `app_id`、`channel_id`、十进制元字符串 `money` 和 32 位十六进制 `request_key`。弹层默认选择最早创建的启用应用，用户可以更改；PID 与凭证版本从服务端应用记录读取，不接受客户端传入 KEY。入口使用管理员认证、同源/CSRF 和事务内会话版本复核。

`PaymentChannelTestService` 仅负责认证与输入装配，调用普通 `PayOrderService::createLocked()`，共用外层事务。请求键作为普通商户订单号，复用应用内唯一约束及订单指纹；同应用、同号、同参数返回原单，修改金额或通道明确拒绝。商品名固定为“通道收款测试”，没有独立订单类型或测试分类字段。

已指定通道时由 `PayOrderAttemptService::prepareByChannel()` 冻结通道与配置，不经过轮询路由、不推进游标。`poll_group_id=NULL`、`route_mode=0` 表示未经过轮询组；通道/插件/支付方式的运营开关与限额不参与选择，已保存插件参数及付款识别仍须有效。普通协议入口不接受指定通道参数。

收银台、插件、回调、生命周期、人工操作、统计和导出使用统一规则。打开收银台时，尚未执行的付款材料通过原 POST 接口准备；后台不自动准备。已有材料直接复用；成功后统一进入 `/cashier/success`，重新验证访问 token 和数据库状态，未支付则返回原收银台。隔离环境的 `personal_receipt.test_only` 只标识合成证据，不能通过页面参数开启。

所有订单按 `notify_url` 判断异步通知责任：提供地址则按原规则冻结签名和任务，未提供则不建立任务，不按商品名或入口分支。后台快捷付款未提供外部目标；易支付协议仍按已公布合同要求 notify_url。付款数据计入所选应用统计和通道日额度，没有测试排除逻辑。

## 主要数据关系

| 对象 | 关系与用途 |
| --- | --- |
| 应用 / KEY 历史 | 应用拥有独立接入身份；旧 KEY 版本保留原订单签名责任 |
| 应用 / 轮询组绑定 | 按支付方式选择组，顺序游标在绑定上维护 |
| 通道 / 当前插件配置 | 当前一对一；历史版本和通道快照不可变 |
| 业务单 / 支付单 | 尚未选方式可以没有支付单；当前版本最多一个支付尝试，终态不自动再建一次 |
| 支付单 / 到账流水 | 只保存最终确认绑定；一条实际流水不能换绑另一笔订单 |
| 通知任务 / 尝试 | 一份冻结通知责任对应多次发送记录，首次 ACK 与最近结果分开 |
| 采集运行摘要 / 登录状态 | 文件缓存保存摘要与插件私有状态，登录态永久保留；订单及最终流水仍以数据库为准 |

详细字段、枚举、NULL 与单位见[数据字典](V1-27-数据库表与字段字典.md)。

## 金额、状态、编号

内部金额为整数分，协议金额为十进制元字符串，禁止用 float 转换。`BizOrder.order_amount` 是原金额；监听准备可将 `PayOrder.pay_amount` 改为识别金额，原值与识别上下文保存在 `personal_receipt`，确认时恢复原金额，实收证据另留。

本地订单状态为 CREATED=0、PAYING=1、SUCCESS=2、FAILED=3、CLOSED=4、TIMEOUT=5。插件结果的 `pending/success` 字符串与易支付查询的 0/1 是各自协议，不能混用。固定业务状态用常量和 TINYINT；可扩展诊断 `result_code` 保留字符串。

B/P/N/R 编号为 20 位，创建时间按上海时区，末尾五位安全随机数；唯一索引冲突有限重试，不额外 SELECT 查重。随机号不保证同秒排序，页面使用时间及内部 ID。

## 并发与不可变边界

- 同应用、同外部单号、同参数返回原订单；冲突参数拒绝。不同应用的相同外部号互不影响。
- 默认组关联在安装/配置事务维护，下单不偷偷补建；预览不改变轮询游标。
- 插件按 BizOrder → PayOrder → PaymentChannel 加锁，在通道内分配识别金额或备注，并保存原单 JSON 快照；同通道跨应用共同占用，不同通道独立。没有预约表或专用释放任务。
- 匹配规则读取原单冻结上下文，不因当前参数编辑而改变。同账号多通道只合并登录/查单；一条流水同时符合多个通道时跳过并记录歧义，不强行挑选。
- 同一流水重复到达沿用原确认事实；批量匹配不合单、不拆单，只保存最终匹配。
- 外部 HTTP、用户浏览器返回和数据库提交是不同边界；未知结果不能写成确定失败。
- 自动通知可能重复送达，商户必须以业务订单做最终幂等。

后台/收银台 JSON 使用 `code/message/data/request_id`，成功 code=200；易支付、HTML 与设备回调使用各自响应合同。公开错误不返回 SQL、堆栈或平台原始敏感响应。
