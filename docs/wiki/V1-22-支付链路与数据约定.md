# 支付链路与数据约定

易支付认证复用本次已读取的活动凭证完成验签；旧通知和回跳仍使用原订单冻结的凭证版本。回跳入口在一个一致性事务中完成订单访问校验、首次商户 ACK 核对和签名，与收银台共用商户应答判断；人工补发失败不撤销首次 ACK。此流程只生成返回地址，不改变支付状态。

## 从下单到确认

![支付链路](assets/payment-flow.png)

1. `/submit.php` 或 `/mapi.php` 验证应用与原始签名，再规范化业务参数。
2. `PayOrderService` 按应用和外部订单号幂等建立业务单，冻结 PID、KEY 版本和通知/返回目标。
3. `PayOrderAttemptService` 在建单事务中选路并固定支付单、通道与配置版本；已有尝试复用原记录，不重新选通道。
4. 指定支付方式的下单请求或收银台准备请求在事务提交后由 `PayOrderChannelDispatchService` 创建插件实例、`init` 并调用 `pay()`；明确拒绝与结果未知分别处理。
5. 插件返回公开的 presentation 参数，服务核对通用结构后保存订单快照；前端按注册组件展示二维码或付款链接。接口受理、出现二维码或页面跳转均不推进成功。
6. 手机/PC 与第三方平台共用 notify，经插件认证解析；主动采集按订单驱动，每账号每轮查询最新最多 200 条、不翻页，再按通道初始化插件并整批调用统一 `notify()`，结果列表逐笔确认。
7. 回调服务校验证据与订单归属；生命周期在事务中更新双单并建立通知责任。有 event_key 的监听结果同时保存最终流水、恢复原金额；普通平台订单确认不制造到账流水。
8. `payment:work` 在事务外发送商户通知，按租约回写尝试与结果；业务网站自己完成验签和幂等履约。
9. 收银台取得首次有效商户 ACK 后才允许回跳或显示完成页；无通知地址的普通订单无需等待外部 ACK。轻量查询与展示注册见[收银台页面与扩展](V1-30-收银台页面与扩展.md)。

## 后台指定通道测试

后台 `POST /adminapi/configuration/channel-test` 接受 `app_id`、`channel_id`、十进制元字符串 `money` 和 32 位十六进制 `request_key`。弹层默认选择最早创建的启用应用，用户可以更改；PID 与凭证版本从服务端应用记录读取，不接受客户端传入 KEY。入口使用管理员认证、同源/CSRF 和事务内会话版本复核。

`PaymentChannelTestService` 仅负责认证与输入装配，调用普通 `PayOrderService::createLocked()`，共用外层事务。请求键作为普通商户订单号，复用应用内唯一约束及订单指纹；同应用、同号、同参数返回原单，修改金额或通道明确拒绝。商品名固定为“通道收款测试”，没有独立订单类型或测试分类字段。

已指定通道时由 `PayOrderAttemptService::prepareByChannel()` 复用当前已保存快照，锁内核对配置版本、正文、通道规则及范围归属；不会追加版本或修改通道指针，不经过轮询路由、不推进游标。`poll_group_id=NULL`、`route_mode=0` 表示未经过轮询组；通道/插件/支付方式的运营开关与限额不参与选择，已保存插件参数及付款识别仍须有效。普通协议入口不接受指定通道参数。

收银台、插件、回调、生命周期、人工操作、统计和导出使用统一规则。打开收银台时，尚未执行的付款材料通过原 POST 接口准备；后台不自动准备。已有材料直接复用；成功后统一进入 `/cashier/success/{biz_no}/{token}`，重新验证访问 token 和数据库状态，未支付则返回原收银台。隔离环境的 `personal_receipt.test_only` 只标识合成证据，不能通过页面参数开启。

所有订单按 `notify_url` 判断异步通知责任：提供地址则按原规则冻结签名和任务，未提供则不建立任务，不按商品名或入口分支。后台快捷付款未提供外部目标；易支付协议仍按已公布合同要求 notify_url。付款数据计入所选应用统计和通道日额度，没有测试排除逻辑。

普通轮询选路仍按配置/通道稳定顺序逐项加锁，核对配置版本、范围、冻结快照和规则。同编码插件的准入结果与定义只在本次调用内复用，插件行锁保持到事务结束，不跨事务缓存。取得全部候选锁后统一读取当前时间，检查可用时段，再由一个独立连接按通道批量汇总启用日限制的候选；独立读取避免主事务旧快照，不锁其他订单或写入主事务。日统计仍按支付单创建自然日，使用原业务金额，成功及有效待付款计入；没有占用分组按零计算，本次金额仍须单独满足上限。选择策略、稳定排序与轮询游标用途保持。

## 本地关闭与超时

后台关闭只停止本地等待，不代表撤销平台收款码。管理员会话、双单关联、原金额和状态仍在事务锁内核验，成功订单不能关闭。关闭时间在取得本次必要锁后由 Clock 读取，closed_at 与对应状态更新时间共用该读数；重复关闭保留首次关闭时间。不以请求进入时的时间代替实际处理时间，也不改写付款证据时间。

到期维护先扫描候选号，再在生命周期事务中重新核对状态和期限，不能以扫描结果直接更新。付款认领/回写已经锁定并核验双单时，内部到期处理复用本事务的支付单；payment:work 独立进入时仍自行取得业务、支付及范围锁并核验。不得复用事务外、上轮或未经关联核验的模型。

关闭和超时不删除原付款窗口、识别快照或执行记录。原窗口内的可信迟到到账继续按原证据确认，成功状态不得被维护任务降级；后台维护不重新调用插件 pay() 或把本地关闭当成平台撤销。

## 主要数据关系

| 对象 | 关系与用途 |
| --- | --- |
| 应用 / KEY 历史 | 应用拥有独立接入身份；旧 KEY 版本保留原订单签名责任 |
| 应用 / 轮询组绑定 | 按支付方式选择组，顺序游标在绑定上维护 |
| 通道 / 当前插件配置 | 当前一对一；历史版本和通道快照不可变 |
| 业务单 / 支付单 | 尚未选方式可以没有支付单；当前版本最多一个支付尝试，终态不自动再建一次 |
| 支付单 / 到账流水 | 监听只保存最终确认绑定；一条实际流水不能换绑另一笔订单，普通平台订单确认可以无流水 |
| 通知任务 / 尝试 | 一份冻结通知责任对应多次发送记录，首次 ACK 与最近结果分开 |
| 采集运行摘要 / 登录状态 | 文件缓存保存摘要与插件私有状态，登录态永久保留；订单及最终流水仍以数据库为准 |

详细字段、枚举、NULL 与单位见[数据字典](V1-27-数据库表与字段字典.md)。

## 金额、状态、编号

内部金额为整数分，协议金额为十进制元字符串，禁止用 float 转换。`BizOrder.order_amount` 是原金额；监听准备可将 `PayOrder.pay_amount` 改为识别金额，原值与识别上下文保存在 `personal_receipt`，确认时恢复原金额，实收证据另留。

退款上限取 `PayOrder::receivedAmount()`，即成功确认时保存的 `ext_json.personal_receipt.notified_amount`；不是 `originalAmount()`、成功后恢复的 `pay_amount` 或二维码提示金额。剩余额度扣除退款表中成功、处理中和未知的金额，失败不占用；实际支付依据缺失时拒绝申请。后台和易支付接口共用原单锁与额度核验，原付款状态和通知不因退款改写。

认领时在原支付单锁内只执行一次退款汇总，同时得到已占用额度和是否存在未决申请；保留非失败申请占用额度、处理中或未知申请阻止后台新申请的原判断。原单锁仍负责串行化同单新增和完成，不能以只读汇总代替交易锁。

后台 `POST /adminapi/orders/refund` 复用登录、写保护和敏感操作限流，正文仅含 `biz_no`、正数元字符串 `refund_amount`、32 位小写十六进制 `request_no`、`current_password` 和可选 `reason`。申请号由详情接口生成，在同一表单内保持不变；浏览器不提供管理员、应用或插件身份。管理员密码复核后，认领事务按管理员→业务单→支付单锁定，复核身份版本、成功状态与额度，并原子记录退款申请和人工操作；提交后才调用插件。后台存在处理中或未知申请时不接受新申请，同号读取仍返回原结果。接口返回的业务状态字段才表示退款结果，后台 HTTP/JSON 请求成功不代表退款成功。

监听到账和人工确认在交易事务内将付款时间、真实渠道交易号写入支付单的 `paid_at`、`channel_trade_no`。手机/PC 监听未取得真实平台交易号时保持 NULL，稳定事件引用同时用于生成缺失的 channel_order_no，按原事件键和摘要去重。普通平台订单确认保存平台受理单号 `channel_order_no`；epay 不把 trade_no 复制到 channel_trade_no。时间只写正式列，epay notify 未提供实际付款时间时记录首次确认接收时间。`ext_json.personal_receipt` 不重复保存时间或交易号，沿用现有金额快照；只有真实流水才保存 event_key。完整合同见[插件开发](V1-23-支付插件开发.md#普通平台订单确认)。

notify 和 pay 的 success 统一返回平级字段，paid_amount 保持原业务金额，received_amount 承接原 receipt.amount。paid_at 必填，来源缺失取本次接收时间；channel_order_no 必须有稳定引用，channel_trade_no 只保留真实流水号。监听 event_key 非空，普通 API 为 null，不能据此绕过已准备监听订单的流水核验。原文只由 raw 提供。

本地订单状态为 CREATED=0、PAYING=1、SUCCESS=2、FAILED=3、CLOSED=4、TIMEOUT=5。插件结果的 `pending/success` 字符串与易支付查询的 0/1 是各自协议，不能混用。固定业务状态用常量和 TINYINT；可扩展诊断 `result_code` 保留字符串。

后台订单读模型增加 `display_status/display_status_label`，不写入数据库：未退款沿用原支付状态，退款进度用 `refund_partial/refund_full/refund_processing/refund_unknown/refund_failed`。未知优先于处理中，未决优先于部分/全部退款；只有成功退款累计等于已确认实付才是全退。仅有失败申请时展示编码为 refund_failed，主标签仍为支付成功，辅文为退款未成功。原 `status/status_label` 和对外易支付状态不变。

列表、详情与 CSV 共用退款汇总及展示计算。列表按本页支付号一次聚合退款金额，详情复用已读取申请；只返回摘要，不把整批申请或退款提交号放进列表。后台 status 筛选接受原 0—5 或上述退款编码，数字 2 表示支付成功（含退款），退款筛选在分页前执行并与总数、导出共用入口，不直接将一对多申请连接到订单结果。订单行新增 refunded_amount、refund_pending_amount、refundable_amount，均为元字符串，实付未知或未支付时 refundable_amount 为 null；未决金额包括处理中和未知，失败不占用。详情原 refund_summary 合同及申请号用途不变。

退款筛选使用相关 `EXISTS`，按候选业务单的 `active_pay_no` 等值限定退款记录后分组，不先对全部退款历史生成汇总派生表。日期、应用等条件仍作用于业务单；退款条件满足后才计数和分页，导出沿用同一条件。只有部分/全部退款筛选关联唯一原支付单读取实付 JSON，按同组唯一实付值比较累计成功金额；其他退款筛选不读取支付表或 JSON。前端颜色统一按 `display_status` 映射，文案只用于展示。

订单的通道、轮询组、支付方式和商户通知筛选也按当前业务号使用相关 `EXISTS`；无通知任务使用 `NOT EXISTS`，不先展开全部历史通知号。支付方式通过支付单方式 ID 关联字典；曾确认通知仍按 `first_ack_at` 核对。列表、计数和导出共用条件，日期范围、分页方式及单行归属不变，不把发送尝试接入外层结果。

只读通知列表及订单中的通知摘要只查展示字段，不加载冻结通知正文、凭证或认领令牌；到账列表不加载完整证据 JSON，关联支付单只读取支付号、业务号和收款范围。完整详情、发送认领和交易加锁读取仍保留原字段与核验，不将这些只读投影用于更新。

B/P/N/R 编号为 20 位，创建时间按上海时区，末尾五位安全随机数；唯一索引冲突有限重试，不额外 SELECT 查重。随机号不保证同秒排序，页面使用时间及内部 ID。

## 并发与不可变边界

- 付款、按支付号回调及退款共用原单快照读取和结构/归属核验；不回退活动配置，不按当前插件版本拒绝旧单。各动作的权限、方式、金额、状态及锁内复核保持独立，公共读取不增加事务或锁。
- 支付单 payment_context 不再写入没有消费方的固定 version 键；配置版本、插件版本及建单指纹中的版本标识保留，不改写历史指纹或添加旧 JSON 格式兼容。
- 同应用、同外部单号、同参数返回原订单；冲突参数拒绝。不同应用的相同外部号互不影响。
- 易支付按支付号查询时复用同一事务已读取的支付单；应用归属、业务单与支付单关联及金额核对保持，按商户订单号查询仍读取其对应支付单。
- 插件参数保存由 Editor 在事务入口鉴权、锁定配置及通道并核对版本；子服务复用已锁模型，继续核验 schema、材料与范围，实际写入后的必要回读保留。
- 默认组关联在安装/配置事务维护，下单不偷偷补建；预览不改变轮询游标。
- 选路批量读取启用组成员的候选通道，再按配置 ID、通道 ID 的稳定顺序加锁；启停、方式、快照、金额、日额度及可用时段仍在锁内复核。
- 本地关闭在生命周期事务内锁定管理员并复核身份及会话版本，失效会话不能关闭订单。
- 插件按 BizOrder → PayOrder → PaymentChannel 加锁，在通道内分配识别金额或备注，并保存原单 JSON 快照；同通道跨应用共同占用，不同通道独立。没有预约表或专用释放任务。
- 匹配规则读取原单冻结上下文，不因当前参数编辑而改变。同账号多通道只合并登录/查单；一条流水同时符合多个通道时跳过并记录歧义，不强行挑选。
- 回调入口已读的目标支付单仅用于定位生命周期锁，不再重复普通查询；进入事务仍按原顺序重新锁定业务单、支付单和范围，重新核对金额、状态与归属。
- 同一流水重复到达沿用原确认事实；批量匹配不合单、不拆单，只保存最终匹配。
- 外部 HTTP、用户浏览器返回和数据库提交是不同边界；未知结果不能写成确定失败。
- 自动通知可能重复送达，商户必须以业务订单做最终幂等。

## 付款准备中断

付款准备的执行租约只控制当前调用权，不是付款有效期，也不证明平台操作成功或失败。同一订单同时收到准备请求时，只有取得当前执行令牌的请求可以调用插件；其他请求读取原执行状态。

若请求进程在认领后中断，租约有效期内继续等待。租约到期后，下单重投或收银台准备请求可以在原支付单上重新准备；`payment:work` 不承担恢复付款准备。插件已经写入的识别金额、备注、首次发起时间和付款窗口继续复用，不新建支付尝试或重新选路。

不存在插件重放开关；后台不因租约到期主动调用插件。结果未知不能当作确定失败，插件对外请求仍使用原单号，退款未知不重发。旧令牌、过期执行结果以及支付成功后返回的付款准备结果，均不能覆盖当前交易事实。并发和中断的验证方法见[业务边界与回归验收](V1-32-业务边界与回归验收.md)。

后台/收银台 JSON 使用 `code/message/data/request_id`，成功 code=200；易支付、HTML 与设备回调使用各自响应合同。公开错误不返回 SQL、堆栈或平台原始敏感响应。

## 收款回调记录与成功流水

`ma_pay_callback_log` 是所有来源统一的收款回调记录，后台仅设 `/admin/callbacks`，管理 API 为 `GET /adminapi/callbacks/list` 和 `GET /adminapi/callbacks/detail?id=…`。列表按接收时间分页，通道、支付号及请求号有普通索引，不使用 JSON 搜索关联流水；正文仅在详情读取；成功监听记录核对原支付单和事件键后展示对应证据，不给拒绝记录附上其他回调的成功依据。

独立回调列表由查询服务开启只读事务；订单详情已在订单历史事务内核对业务单，调用同事务组合方法复用分页和映射，不再次开启事务。组合方法保留事务前提检查，不放开全局嵌套事务限制。

`ma_receipt_flow` 保留真实成功流水的证据和消费唯一约束，仍由生命周期在确认事务中创建、绑定。流水内不再单独保存 remark 或 source_payload_digest；原文只在受控回调日志保存，稳定交易摘要排除 raw、兜底时间及备注。它不是第二份后台日志：不存接收失败或普通 API 平台的虚构流水，不再提供独立管理入口。插件/事件键、插件/真实交易号及支付号的原唯一约束、金额/归属/窗口核验不变。

成功或重复回调的日志与双单、成功流水及应有商户通知一起提交；交易回滚后，拒绝或异常只通过短事务记录诊断元数据，不保存未匹配收款内容。日志持久化失败明确上抛，不发送成功 ACK。HTTP 认证后明确非收款可记录“忽略”；正常采集无匹配不逐项记录，批次错误只留受限诊断，逐笔业务异常仍隔离。

通知正文只保存插件 raw：手机/PC 是已认证原始表单字段，主动采集是最终匹配的一条来源记录，API 是原回调协议参数。服务不按结果数量猜测正文，不保存整批、候选、配置、请求头或登录态，也不把标准成功字段当原文。上限 8192 UTF-8 字节，保存截断标记与截断前 SHA-256；该摘要不用于交易防重。失败或忽略记录不保存正文、实收和时间。多个结果各写一行，共用请求号；重复通知可有多行，不重复创建商户通知。已有旧日志不重建成伪原文。

付款执行审计写入 `ma_pay_order_operation_log`，系统操作者为 NULL，保留执行令牌摘要及前后状态；人工动作继续核验管理员并使用原审计规则。不新增日志类型、汇总表、队列或历史转换流程。

## 通知责任与发送

创建通知责任时，成功消息组装入口统一核对业务单、支付单的成功状态与关联；未提供通知地址的订单也经过该核对，然后结束处理，不读取通知密钥或创建发送任务。存在通知地址时，在原成功事务内冻结目标和签名；人工暂缓、重复确认及后续派发机制保持一致。

通知按冻结参数构造本次完整请求地址，重试不重新签名。发送前只核对当前任务、当前尝试及认领状态，不扫描历史尝试记录是否连续；认领令牌、有效期、尝试序号和首次有效应答仍保留。每次发送记录 HTTP 状态、耗时、受限响应正文及截断标记。

最终地址统一在消息组装入口检查实际 query 字段和完整长度；原地址中的 query 已合并进冻结签名参数，不再额外解析随后会被替换的旧内容。认领端保留冻结载荷身份和值类型核验，不重复解析组装好的完整地址；发送前的网络目标检查继续执行。通知和回跳完整地址上限为 16384 个字符。

新订单按应用允许的域名/IP 检查通知与回跳地址，支持合法 HTTP(S) URL 的 1～65535 端口，不保留固定端口白名单。主机规范化只用于授权比较，IPv6 在 URL 中使用方括号；不修改原签名参数、实际端口或查询串。已生成的通知继续使用冻结地址和签名；修改允许主机不会重写原通知。每次发送前重新检查 DNS/IP 并绑定连接，A/AAAA 及实际连接核对均支持 IPv6；浏览器回跳不执行服务器网络限制。

商户通知默认要求目标属于允许的公网地址，连接绑定本次已核验的 DNS 结果并核对实际连接 IP；开发例外仍限定环境、主机和端口。插件 SDK 请求按插件配置的平台地址正常连接，可对接内网平台；该规则不会放宽商户通知地址限制。

扫描候选时优先取发送租约已过期的任务；若已达到本批上限，直接返回该批，不再查询不会被采用的待发任务。未满时继续读取待发任务并去重、截取上限；候选资格和认领状态仍在逐条短事务内重新核对。

发送器只读取一次 HTTP 状态及完整受限响应正文，同一正文用于 ACK 判断与日志截断。ACK 仍要求 2xx 状态及小写 `success`，只忽略首尾空格、制表符和换行；日志片段不参与成功判断。

若发送进程中断或停顿到租约过期，系统先把该次尝试记为 `lease_expired_unknown`（结果未知），再按原退避规则安排下一次发送。旧进程随后拿到 `success`，也必须核对当前令牌、尝试序号和租约；已经失去调用权时返回 `lease_lost`，不覆盖新尝试和首次有效确认时间。

这只能防止旧结果覆盖数据库，不能撤销商户已经收到的请求。因此商户仍须验签并按订单幂等履约，不能将同一通知的重试当成新的收款。
