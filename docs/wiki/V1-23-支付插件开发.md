# 支付插件开发

插件解释平台协议和收款识别，服务负责装配、归属检查及最终生命周期，SDK 负责平台 HTTP、签名和解析。四个主类直接实现接口，不继承公共支付 Base，也不增加 capabilities/source 准入层。

## 1. 放置与发现

主类位于 `app/common/payment/YourPayment.php`，SDK 位于 `app/common/sdk/平台目录`，接口位于 `app/common/interface`。固定目录扫描具体类并拒绝重复插件编码，数据库中的类名不能作为任意执行入口。

新增/修改代码后在后台刷新插件目录，核对字段并启用。新插件默认停用；插件代码升级后重启两个常驻命令。只刷新目录不自动重写已有通道配置或旧订单快照。

## 2. 选择实际需要的接口

| 接口 | 用途 |
| --- | --- |
| `PaymentInterface` | 元信息、初始化、重放能力及 pay/query/close/refund |
| `ChannelNotifyInterface` | 继承 PaymentInterface，定义 notify、notifySuccess、notifyFail，处理 HTTP 推送与协议应答 |
| `ReceiptCollectorInterface` | 继承 PaymentInterface，定义 collect、matchReceipts、prelogin 及 isPreloginEnabled，处理整套主动监听 |

接口目录只有这三个合同。插件同时需要 HTTP 推送和主动查询时可实现两个扩展接口；仅采集的插件不用实现 HTTP 通知或返回占位 ACK。后台通道“接入信息”只为实现通知接口的插件提供回调地址；仅采集插件显示由后台任务查询。

预登录由采集插件的代码元信息 `prelogin` 决定，未声明默认为 false。`isPreloginEnabled(): bool` 读取该声明，工厂集中判断，服务不根据类名或账号字段猜测。完整输入/输出、声明示例、状态缓存与预算见[主动采集合同](V1-25-主动采集与会话协作.md)。

仅手机推送的插件不实现主动采集接口；没有此接口，watch 不调度它。平台专项诊断放 `tests/diagnostics`，不新增正式守护命令。

## 3. 元信息、配置与实例

提供唯一 code、名称、版本、支持的支付方式、可选纯文本 description 和 `config_schema`。`$paymentInfo` 是代码声明，不是订单或真实账号信息。字段规则见[完整 schema 合同](V1-24-config-schema字段规则.md)。

单订单动作创建独立实例并 `init(array $channelConfig)`；批量采集/匹配直接使用 orders/channels 输入，不依赖上一次单通道 init 的残留设置。输入包含原版本插件设置，以及服务提供的 channel_id、api_config_id、receipt_scope_key 等运行字段；不能允许请求覆盖这些保留字段，也不序列化给前端或日志。

## 4. pay 输入

```php
[
    'pay_no' => 'P2026100915304505189',
    'biz_no' => 'B2026100915304512345',
    'pay_type_code' => 'alipay',
    'amount' => 1234, // 原业务金额，整数分
    'expire_at' => '2026-10-09 15:35:45', // 上海时间
    'extra' => [],
]
```

`canRetryPay()` 在初始化之前也必须可读。仅无外部副作用或平台严格按原单幂等时返回 true，不能因为“多数时候成功”就允许重放。

## 5. 当前静态码结果

```php
[
    'status' => 'pending',
    'pay_no' => $order['pay_no'],
    'paid_amount' => null,
    'chan_order_no' => null,
    'chan_trade_no' => null,
    'pay_type' => $order['pay_type_code'],
    'pay_product' => 'receipt',
    'pay_action' => 'qrcode',
    'presentation' => [
        'pay_page' => 'page',
        'pay_params' => [
            '_page' => 'receiptQrcode',
            'qrcode_content' => $qrText,
            'qrcode_image_url' => $verifiedLocalImageUrl,
            'order_money' => '12.34',
            'receipt_money' => '12.35',
            'remark' => null,
        ],
    ],
]
```

这是假设已经完成识别值准备的结果形状，不可在实际插件中硬编码示例金额。当前服务只接受固定页面映射，不接受任意模板路径；V2 的其他 presentation 模式未全部实现。

现有监听插件在自己的短事务中分配识别金额/备注，遵循核心锁顺序。服务派发插件时不持有外部 HTTP 事务；新插件不能把平台请求放进可重试数据库闭包。

## 6. notify 与整批匹配

认证并解释平台记录后返回：

```php
[
    'status' => 'success',
    'pay_no' => $matchedPayNo,
    'paid_amount' => $originalAmountInCents,
    'chan_order_no' => $platformTradeNo,
    'chan_trade_no' => $platformTradeNo,
    'paid_at' => $paidAt,
    'receipt' => [
        'pay_type' => 'alipay',
        'event_key' => $stableEventKey,
        'trade_no' => $platformTradeNo,
        'amount' => $receivedAmountInCents,
        'paid_at' => $paidAt,
        'remark' => $payerRemark,
    ],
]
```

这是插件识别结果，还没有完成数据库确认。插件不在 notify 中提前恢复金额或预写最终流水；服务核验证据后通过生命周期统一提交。事件键稳定、实际收款金额和平台号真实，缺失可空字段不伪造。

`matchReceipts($receipts, $orders, $channels)` 接收本次单页响应的整个 `list<{record,consumed_pay_no}>` 批次及对应原单/通道版本，返回逐笔匹配结果；未匹配不返回，同批不重复选择同一订单。一条流水只消费一次。手机保留对应实现的单候选规则；账单/码牌按付款窗口和距发起时间选择，等距稳定排序。

## 7. 其他动作与失败语义

query 不能用本地二维码证明成功；close 对静态码只能表达本地关闭；refund 是否支持由原订单插件决定。没有能力时抛 `UnsupportedPaymentOperationException`，明确拒绝用 `PaymentDefinitiveException`，已发送但结果不明用 `PaymentUncertainException`。

ACK 采用平台实际要求；当前手机监听成功/失败正文为 `success`/`fail`。不要统一套后台 JSON。

## 8. 最小完整骨架

下载[ExamplePayment.php](examples/ExamplePayment.php)。它完整实现基础接口，可用于核对类签名、元信息和动态字段，但所有交易动作明确拒绝，**不是可收款插件**。实现真实协议后再放入正式目录，不能为通过展示而返回假成功。

验证至少覆盖字段类型、初始化、真实协议认证、金额时间、重复/迟到、批量匹配、异常和重放边界；采集插件再检查单次 200 条上限、账号归并、永久登录态、重启恢复、预登录与重复流水。真实平台验证与合成测试分别记录。
