# 支付插件开发

后台表单定义来自已同步的数据库插件目录。单项配置按 code 读取一条记录，与列表共用版本、名称、类名、支持方式、schema 和描述的同步检查；固定代码目录发现仍由工厂负责。插件列表的关联通道数一次按插件编码分组统计，排除已删除通道，不增加持久统计或跨请求缓存。

插件解释平台协议和收款识别，服务负责装配、归属检查及最终生命周期，SDK 负责平台 HTTP、签名和解析。内置插件继承薄 BasePayment，共用配置保存及元信息读取；支付、网络和匹配逻辑仍在各插件。没有插件类型枚举或 capabilities/source 准入层，主动采集通过采集接口调度。

## 1. 放置与发现

主类位于 `app/common/payment/YourPayment.php`，SDK 位于 `app/common/sdk/平台目录`，接口位于 `app/common/interface`。安装及目录管理全量发现固定目录内的具体类，并拒绝重复插件编码；刷新后完整定义及编码到类的映射保存到数据库。

打开单个插件配置、按编码准备付款、回调或退款时，读取已同步的目标映射，不为寻找一个编码扫描或实例化其他插件。映射仅允许 `app\common\payment` 命名空间下、固定目录内真实存在且实现 PaymentInterface 的可实例化类，并核对实际元信息编码；缺失或不一致明确报错，不回退全目录扫描。配置表单继续比较版本、名称、支付方式、schema、描述和类映射的同步状态。数据库类名不能成为任意执行入口。

插件目录发现或单项目标读取时核对接口、编码及元信息；执行时创建独立实例并注入配置，不缓存带通道配置的实例。配置值在后台保存、启用时校验，初始化不重复执行 schema 验证。已有显式隔离注册仍只在受约束的本地测试入口生效，不放宽正式文件范围。

新增/修改代码后在后台刷新插件目录，核对字段并启用。新插件默认停用；插件代码升级后重启两个常驻命令。只刷新目录不自动重写已有通道配置或旧订单快照。

配置的同一字段格式由保存/启用入口按 schema 校验，运行时不再重复完整的配置值检查。例如银行卡号允许空格或短横线分组，插件运行时只去掉分组符，供展示与卡尾核对。收到的消息仍须验证来源、金额、付款时间、卡尾和订单归属；配置合法不代表到账事实已核验。

## 2. 选择实际需要的接口

| 接口 | 用途 |
| --- | --- |
| `PayPluginInterface` | init 及元信息读取；BasePayment 提供统一实现 |
| `PaymentInterface` | 继承 PayPluginInterface，定义 pay/query/close/refund/notify/notifySuccess/notifyFail |
| `ReceiptCollectorInterface` | 继承 PaymentInterface，定义 collect/prelogin/isPreloginEnabled |

所有支付插件都有统一 notify；仅采集插件拒绝 Request 输入，其 ACK 方法明确抛不支持异常。当前后台为采集插件展示后台查询模式，其他插件展示 HTTP 回调地址；该展示规则不代替插件的来源认证。收银台展示继续使用前端组件，不增加后端页面接口。

预登录由采集插件的代码元信息 `prelogin` 决定，未声明默认为 false。`isPreloginEnabled(): bool` 读取该声明，工厂发现时核验声明，调度器通过接口直接读取，不根据类名或账号字段猜测。完整输入/输出、声明示例、状态缓存与预算见[主动采集合同](V1-25-主动采集与会话协作.md)。

仅手机推送的插件不实现主动采集接口；没有此接口，watch 不调度它。平台专项诊断放 `tests/diagnostics`，不新增正式守护命令。

## 3. 元信息、配置与实例

提供唯一 code、名称、版本、支持的支付方式、可选纯文本 description 和 `config_schema`。`$paymentInfo` 是代码声明，不是订单或真实账号信息。字段规则见[完整 schema 合同](V1-24-config-schema字段规则.md)。

元信息通过接口方法返回；下表约束由 `PluginDefinition` 和插件目录发现流程检查，不是通道配置值：

| 方法 / 元信息 | 类型与约束 | 示例或用途 |
| --- | --- | --- |
| `getCode()` / code | 1～64 个 ASCII 字符；小写字母开头，后续只能是小写字母、数字或下划线；全目录唯一 | `example_receipt`；不能使用中文、连字符或类路径 |
| `getVersion()` / version | 1～32 个 ASCII 字符；字母或数字开头，后续可含字母、数字、下划线、点和连字符 | `1.0.0`、`1.1.0-beta`；用于展示和记录，不负责选择多份代码或限制启用 |
| `getName()` / name | 非空字符串 | 后台显示名称，例如“示例收款” |
| `getEnabledPayTypes()` / pay_types | 非空列表；每项为 1～32 个 ASCII 字符，小写字母开头，后续只能是小写字母、数字或下划线 | `['alipay', 'wxpay']`；这里声明支持范围，方式是否存在、启用仍由目录和选路检查 |
| `getDescription()` / description | UTF-8 纯文本，最多 8192 字节；无说明时返回空字符串 | 不返回 HTML；空说明不显示说明区 |
| `getConfigSchema()` / config_schema | 有序字段列表，最多 128 项 | 属性、默认值与校验规则见字段规则文档；无参数时返回 `[]` |

上述元信息由 protected $paymentInfo 声明，基类方法在 init 前即可读取，不依赖通道账号。BasePayment 只实现元信息、init 和 getConfig，不提供 HTTP、匹配或状态推进。主动采集插件的 isPreloginEnabled 读取布尔 prelogin，未声明为 false。

单订单动作创建独立实例并调用 init(array $config)，只传原版本插件配置。通道标识、订单及请求环境均放在动作参数；不把系统字段加入配置 JSON。collect/prelogin 接收本轮订单/通道输入，不依赖单通道初始化状态；采集结果按通道创建并初始化独立实例，再调用 notify。

下单、回调和退款通过 PaymentPluginFactoryService::initialize 装载配置；保存入口负责 schema 值校验。init 不执行平台请求。pay 在执行认领提交后调用；上传资产地址作为 pay 的 assets 参数提供，回调和退款不读取图片。元信息按类缓存，执行实例保持独立，代码更新后重启常驻进程。

付款、按支付号进入的回调及退款共用 PaymentChannelRevisionService::forOrder 读取原单快照，核对通道、插件、配置版本与冻结结构。它不校验配置值、不读取当前配置补缺，也不比较当前代码版本；支付方式、金额、动作状态及锁内交易核验继续由各入口负责。通道 ID 回调仍走当前配置授权，主动采集仍使用本轮调度快照，不改为这个原单入口。

支付方式使用通用编码规则，实际是否允许新单由目录、插件支持及选路决定；内部建单对象不写死支付宝、微信名单。

HTTP 回调共用 GET|POST /api/pay/{identifier}/notify：通道 ID 使用当前配置，P 开头的 20 位支付号使用原单冻结配置。服务组装 context.channel_id；按支付号进入时另外提供 context.pay_no，插件结果只能属于该单。上下文不与外部请求参数合并；配置中不再注入 pay_no 或其他系统运行字段。

## 4. pay 输入

```php
[
    'pay_no' => 'P2026100915304505189',
    'biz_no' => 'B2026100915304512345',
    'channel_id' => '12',
    'pay_type_code' => 'alipay',
    'amount' => 1234, // 原业务金额，整数分
    'expire_at' => '2026-10-09 15:35:45', // 上海时间
    'subject' => '商品名称',
    'client_ip' => '203.0.113.10', // 业务单冻结的付款人 IP，示例地址
    'notify_url' => 'https://mpay.example.com/api/pay/P2026100915304505189/notify',
    'return_url' => 'https://mpay.example.com/cashier/pay?biz_no=...&token=...',
    '_env' => 'mobile',
    '_submit_type' => 'page', // page / api，由服务入口确定
    'assets' => ['receipt_qrcode_image' => '/uploads/example.png'], // 仅示意派生公开地址
    'extra' => [],
]
```

_env 与 _submit_type 是平级动作参数。submit 固定 page，设备从浏览器 UA 识别，忽略输入 device 的展示选择；mapi 固定 api，device 只允许 pc/mobile/qq/wechat/alipay/jump，缺省为 pc，不使用业务服务器 UA 猜设备。jump 是协议跳转选项。原始请求先验签，再组装内部参数，外部同名参数不能覆盖内部字段。

pay 只由下单或收银台请求触发。重复请求复用材料；未完成执行在租约到期后可由普通请求使用原单号重新准备，原识别事实、付款窗口和执行令牌核对保持。结果未知不是确定失败，退款未知不自动重发；payment:work 不恢复付款准备。

pay 抛出 PaymentDefinitiveException 或 PaymentUncertainException 时，插件/SDK 必须先去除说明中的凭证及完整报文。服务通过 payment.execution_error 技术日志记录支付号、通道、插件、调用关联号、execution_rejected/execution_uncertain 分类和 error_message；说明最多保留 2048 个 UTF-8 字节，超长由既有 SafeLogger 标记截断。日志描述本次插件调用，不替代生命周期对执行令牌、期限和当前订单状态的核对；不把说明写入订单快照或新增公开响应字段。其他程序异常仍按原路径上抛。

### 异常选择

复用现有异常，根据失败原因选择，不为每个平台增加异常类或再建立统一异常层级。

| 情况 | 现有异常 |
| --- | --- |
| 本次支付/退款有确定拒绝证据 | `PaymentDefinitiveException` |
| 付款/退款执行结果无法确定，或查询无法确认 | `PaymentUncertainException` |
| 采集认证、网络、限流、流水格式等已分类错误 | `ReceiptCollectionException` |
| 通知认证失败、消息结构或金额格式/范围无效 | `ReceiptMessageException` |
| 插件不支持当前动作 | `UnsupportedPaymentOperationException` |

普通配置错误及业务冲突继续用 `BusinessException`。快照损坏、已保存结果无法读取、账号缓存或恢复提示写入失败属于技术故障，保留 `RuntimeException`；内部调用约定错误保留 `LogicException`，按原故障路径上抛。不能把这些故障或网络超时换成“平台明确拒绝”，也不捕获任意异常后返回空成功。手机通知只在外部金额转换处将原生参数错误转为已有消息异常，保留金额上限和原来源/时间/匹配检查。

插件/SDK 在框架初始化后运行，使用应用上海时区。`Clock` 用于当前时间和业务期限；`DateTimeImmutable` 仍用于截止参数及严格日期解析。本地完整日期不重复指定时区；时间戳仅输出字符串时可用 `date(格式, 秒数)`，毫秒先按原协议转秒。确实保留 `@timestamp` 对象或处理 UTC/偏移时间时仍须转换到上海时区，不用当前接收时间补造付款时间。详见[时间处理](V1-21-开发环境与目录结构.md#时间处理)。

## 5. 当前静态码结果

`pay()` 返回 `pending` 时，下列键除 `chan_order_no` 外都必须提供。可空字段明确返回 `null`；`chan_order_no` 的补缺规则单独见下表。

| 字段 | 类型与约束 | 含义 |
| --- | --- | --- |
| status | 字符串 `pending` | 付款材料已准备，不代表到账 |
| pay_no | 原输入支付号字符串；边界校验最长 64 字符，当前系统生成 20 位 | 原样返回，不自行生成或替换 |
| paid_amount | `null` | 尚未确认业务支付金额 |
| chan_order_no | `null` 或非空字符串，最多 128 字节 | 已有值保留；缺失、null 或空串时使用 chan_trade_no，两者都无值则为 null |
| chan_trade_no | `null` 或非空字符串，最多 128 字节，键必须提供 | 仅填写真实交易号；不从 chan_order_no、事件键或本地单号反向补造；静态码准备阶段通常为 null |
| pay_type | 支付方式编码，沿用原输入 `pay_type_code` | 1～32 个 ASCII 字符，语法同元信息中的支付方式 |
| pay_product / pay_action | 各为 1～64 个 ASCII 字符，字母开头，后续只能是字母、数字或下划线 | 分别记录插件实际使用的产品和动作，例如 `alipay_qrcode` / `display_qrcode`，不是中文标签或 URL |
| presentation | 仅含 `pay_page`、`pay_params` 的关联数组 | 页面标识、公开参数类型和大小见[展示字段约束](V1-30-收银台页面与扩展.md#展示字段约束) |

`pay_product` 和 `pay_action` 是插件声明的产品与动作标识，用于追踪本次付款准备路径，不由服务根据插件名或页面反推。插件有多个产品/动作时，按实际执行分支填写；它们不作为支付成功证据，也不混入后续采集的查询接口名称。当前静态码插件没有在 pay() 中请求平台下单，具体值如下：

| 插件及实际分支 | pay_product | pay_action | 动作含义 |
| --- | --- | --- | --- |
| 支付宝手机收款监听 | alipay_qrcode | display_qrcode | 展示支付宝收款码 |
| 微信手机/PC 收款监听 | wechat_qrcode | display_qrcode | 展示微信收款码 |
| 收钱吧码牌流水 | shouqianba_qrcode | display_qrcode | 展示收钱吧收款码 |
| 支付宝账单：金额/手动备注 | alipay_qrcode | display_qrcode | 展示支付宝收款码 |
| 支付宝账单：自动金额和备注 | alipay_transfer | create_transfer_link | 生成支付宝客户端转账入口，供付款人操作 |
| 中行、建行、工行银行卡收款 | bank_transfer | display_bank_account | 展示银行、户名与卡号，付款人按公共应付金额转账 |

这些是当前插件定义的标识，不是核心的产品白名单。服务只校验通用格式并随 presentation 保存。后台“订单详情 → 处理记录 → 技术信息”读取原单的两个值；未完成材料准备时显示“—”，不读取当前配置补写。生成转账入口不表示已调用平台资金划转接口。

若 `pay()` 已取得真实成功证据，可返回 `success` 并按下一节提供监听流水或平台订单确认；chan_trade_no 仍须明确提供，chan_order_no 沿用上述单向补缺规则，此时不再要求 presentation。不能用二维码、受理成功或页面跳转替代收款证据。当前七个监听插件及 epay 插件准备付款材料时均返回 pending。epay 的 pay_product 为 `epay_v1`，pay_action 按实际分支为 `submit` 或 `mapi`。

```php
[
    'status' => 'pending',
    'pay_no' => $order['pay_no'],
    'paid_amount' => null,
    'chan_order_no' => null,
    'chan_trade_no' => null,
    'pay_type' => $order['pay_type_code'],
    'pay_product' => 'alipay_qrcode',
    'pay_action' => 'display_qrcode',
    'presentation' => [
        'pay_page' => 'page',
        'pay_params' => [
            '_page' => 'receiptQrcode',
            'qrcode_content' => $qrText,
            'qrcode_image_url' => $verifiedLocalImageUrl,
            'instruction' => 'manual_remark', // 普通扫码用 scan，并令 remark=null
            'remark' => $preparedRemark,
        ],
    ],
]
```

这是假设已经完成识别值准备的结果形状。插件生成并校验具体公开材料，服务校验通用结构后保存 presentation 快照。前端 page 当前注册 receiptQrcode、alipayTransfer、bankTransfer 和 dynamicReceipt，另有 jump 直接模式；新增页面实现并注册前端组件，公共后端不需要配套增加平台展示类，不接受任意模板路径。金额、备注与有效期从本单冻结事实生成，页面只显示一处应付金额。pay_params 只能放插件明确挑选的公开 JSON，不得直接返回配置、整个 ext_json 或上游原文；服务不会猜测并删除其中的秘密字段。倒计时读取公共 order.expires_at/server_time，不在每个页面参数中注入时间或二维码编码规格。扩展步骤见[收银台页面与扩展](V1-30-收银台页面与扩展.md)。

现有监听插件在自己的短事务中按 BizOrder → PayOrder → PaymentChannel 顺序加锁，再按 channel_id 分页读取有效待付订单快照。无准备快照的初始化金额不占用识别值，完整快照直接复用，部分损坏的快照拒绝重新分配。金额模式保持通道内金额唯一；备注模式分配通道内唯一四位备注，同时必须核对金额。同一通道跨应用共同占用，不同通道互不占用。模式切换仍尊重旧单快照，不能新增与旧金额识别单同额的备注订单。

订单本身保存准备事实，不建立识别预约表，不依赖缓存来保证唯一。插件决定金额、备注及付款窗口，服务校验标准金额、原单归属和重复流水，再统一提交交易。服务派发插件时不持有外部 HTTP 事务；新插件不能把平台请求放进可重试数据库闭包。

当前七个监听插件在 `ext_json.personal_receipt` 保存 `original_amount`、`receipt_amount`、`match_mode` 和 `remark`。金额均为整数分；偏移展示由 `receipt_amount - original_amount` 计算，不额外保存 `offset_amount`。到账后由生命周期补充实际收款证据，插件返回的公开付款参数仍与内部快照分开。三个银行卡插件固定 match_mode=amount、remark=null，不提供备注识别。

## 6. notify 与整批匹配

统一签名为 `notify(Request|array $payload, array $context): array`，返回 **list**，单笔也返回 `[$result]`；多笔返回 `[$a, $b]`。合法采集没有匹配结果，或 HTTP 已认证且明确为非入账消息时返回 []；后者正常 ACK，不创建流水或商户通知。HTTP 实际入账无匹配/匹配歧义、认证、格式或运行错误必须抛异常，不能通过空列表伪装正常忽略。pay/query/close/refund 仍返回单项动作结果。

context 只含必填 channel_id（数字字符串）和可选 pay_no。HTTP 传原始 Request；采集传 `{records: list<{record, consumed_pay_no}>, orders: array<pay_no, order>}`。后者只由内部采集入口构造，orders 复用本轮 collect 的只读调度快照，并限定为本次账号批次覆盖的通道版本；字段与[主动采集订单输入](V1-25-主动采集与会话协作.md#2-订单和通道输入)一致。它是待比对候选，不是已匹配订单，也不包含通道配置集合；消费标记由服务查库提供。HTTP 载荷不能替代内部批次或上下文。

采集插件直接比对批次候选，按当前 context.channel_id 返回结果；不按流水时间另查更大范围，不为每个通道重复读取同一批订单。共享账号的跨通道歧义仍使用整个批次的候选在插件中识别，不跨批次缓存。服务核对原调度范围和真实流水证据，再逐笔提交，各订单独立事务。单笔业务拒绝或普通任务异常记录后继续，数据库异常上抛。HTTP 有失败不能发送整批成功 ACK；首个错误由外层业务应答或全局报告记录，其他错误在逐笔边界记录，不重复记同一错误。重复已确认事实正常幂等，不新建通知。单项 HTTP 日志可关联 flow_id，多项通过各订单日志的 request_id 关联。

下面展示列表中**一项**监听成功结果（notify 返回时还需外包列表）：

```php
[
    'status' => 'success',
    'pay_no' => $matchedPayNo,
    'paid_amount' => $originalAmountInCents,
    'chan_order_no' => $platformTradeNo,
    'chan_trade_no' => $platformTradeNo,
    'receipt' => [
        'pay_type' => 'alipay',
        'event_key' => $stableEventKey,
        'trade_no' => $platformTradeNo,
        'amount' => $receivedAmountInCents,
        'paid_at' => $paidAt,
        'remark' => $payerRemark,
    ],
]
```

这是插件识别结果，还没有完成数据库确认。插件不在 notify 中提前恢复金额或预写最终流水；服务核验证据后通过生命周期统一提交。事件键稳定、实际收款金额和平台号真实，缺失可空字段不伪造。

成功结果的 `status` 固定为 `success`，`pay_no` 必须引用原订单；`paid_amount` 是原业务金额的整数分，必须与原单一致。`receipt.amount` 是实际到账的整数分，两者不能混填。`chan_trade_no` 应与 `receipt.trade_no` 一致；带流水的结果只在 `receipt.paid_at` 提供付款时间，不重复返回外层 `paid_at`。

监听结果继续保留 chan_order_no；pay/notify 的标准结果入口只在该字段缺失、null 或空串时取 chan_trade_no，不覆盖已有值。普通平台成功结果补缺后仍须有有效编号；监听未取得真实交易号时两个编号可同时为 null，事件去重继续使用 event_key，不以合成编号补缺。

生命周期返回 matched=false 时，共用回调入口通过现有 SafeLogger 记录 receipt.confirmation_rejected，包含 pay_no、channel_id、plugin_code、trace_no 及核心原因码。HTTP 通知、主动采集和 pay 成功结果共用此记录，不增加数据表、失败流水或重试机制；结构错误、业务异常及程序故障仍沿原异常路径处理。

### 普通平台订单确认

已认证的平台订单成功不需要构造虚假的收款流水，列表中的单项形状如下：

```php
[
    'status' => 'success',
    'pay_no' => $localPayNo,
    'paid_amount' => $amountInCents,
    'pay_type' => 'alipay',
    'chan_order_no' => $upstreamOrderNo,
    'chan_trade_no' => null,
    'paid_at' => null,
]
```

不提供 `receipt` 键。`chan_order_no` 补缺后必须为非空 UTF-8 字符串、最多 128 字节；已有平台订单号优先，缺失时可使用真实 chan_trade_no，两者都没有则拒绝确认。`pay_type` 须与原单一致；`paid_at` 为上海时间字符串或 null，必须明确提供。平台未给付款时间时，首次确认将服务接收时间记录到订单 paid_at，含义为“系统确认时间”，不宣称是平台实际付款时刻。重复通知不更新该时间，也不新建商户通知任务。

服务在 BizOrder → PayOrder → Scope 的现有锁序内重新核对订单、通道、插件、冻结配置版本、支付方式、金额及原平台订单号，原子更新双单和通知责任。已准备监听 match_mode 或已绑定流水的订单不能改走此分支；监听的来源、金额、付款窗口和流水防重仍沿原流程处理。平台明确报告原单成功时，本地关闭/超时不代表上游未支付；确定失败的订单则拒绝自动改成功。

`channel_order_no` 保存平台受理订单引用，无该编号时可由真实 chan_trade_no 补缺，不设唯一索引；`channel_trade_no` 保留现有“插件编码＋交易号”唯一约束。epay 的 trade_no 只映射前者，不为不同站点引入交易命名空间。同一个本地订单的回调仍必须报告一致的订单引用，不因补缺规则覆盖已保存的不同编号。

普通结果的 chan_trade_no 也可以提供真实交易标识（非空 UTF-8、最多 128 字节），服务按原有交易号唯一约束防重；没有则明确给 null。不根据插件是否实现采集接口决定能否填写，epay 本插件始终不以平台受理单号补造它。

### 标准流水字段

HTTP 通知结果中的 `receipt`、主动采集的 `records` 元素，以及 `notify()` 返回的流水证据共用下表。前六个键必须存在；可空字段没有可靠来源时填 `null`，不能省略或用空字符串代替。文本须为有效 UTF-8；“字节”与“字符”分别按表中单位判断。

| 字段 | 类型 / 可空 | 约束与含义 |
| --- | --- | --- |
| pay_type | string，不可空 | 支付方式编码，1～32 个 ASCII 字符，小写字母开头，后续只能是小写字母、数字或下划线；须与原单方式一致 |
| event_key | string，不可空 | 非空，最多 128 字节；同插件范围内稳定唯一，同一条流水重试时不得改号，不包含认证凭证 |
| trade_no | string 或 null | 非空时最多 128 字节；仅提供可靠的真实平台交易号，没有则为 null；监听合成编号只放在 event_key |
| amount | int，不可空 | 实际到账金额，1～999999999 分；不接受数字字符串或浮点数，并须匹配本单识别金额 |
| paid_at | string 或 null | 上海时间 `Y-m-d H:i:s`，严格的 19 字符有效日期时间；实际自动匹配还须有可靠时间并落在原单付款窗口内 |
| remark | string 或 null | 非空时最多 256 个 UTF-8 字符；是否必需以及如何解析由插件的匹配方式决定 |
| extra | array，可省略，不接受 null | 脱敏的平台补充信息；使用 `JSON_UNESCAPED_UNICODE` 编码后最多 4096 字节，JSON 编码深度上限 16；不能带认证状态或完整原始响应 |

标准流水不接收未声明的顶层字段。服务会根据标准字段及 extra 重新计算 `payload_digest`，插件无需生成或依赖自己传入的摘要。流水备注的 256 **字符**限制与收银台组件 `remark` 的 256 **字节**展示限制用途不同，不能直接视为同一个边界。

稳定事件键是插件开发要求，不能把每次 HTTP 请求的新时间或随机值当作新的真实流水。当前手机兼容适配仍将请求 timestamp 纳入监听编号，改变请求时间的重发不能保证同键去重；其时间语义与现有限制见[手机重发与时间的当前限制](V1-11-微信手机与PC监听.md#手机重发与时间的当前限制)。不要将该限制复制成新插件的推荐实现，也不要据通用幂等约束宣称当前手机路径已解决所有重发情况。

手机在当前通道内保留单候选规则；账单/码牌 notify 一次处理当前通道的整批记录，按原付款窗口、金额和备注识别，按付款时间距发起时间选择，等距稳定排序。共享账号批次保留全部覆盖的版本引用；符合多个通道的记录跳过并记录 ambiguous_channel。同批不重复选择同一订单，已消费流水不得重新分配。

四个内置监听插件均保留金额与手动备注模式；备注能否自动识别取决于实际消息或平台流水是否提供备注，不能猜测缺失值。支付宝账单另提供 alipay_transfer 模式：插件生成携带同一金额和备注的二维码及手机入口，公开页面为 alipayTransfer；最终仍由账单采集按备注＋金额确认，不因打开链接而成功。收钱吧保留付款端输入金额及备注的流程。

## 7. 其他动作与失败语义

query 不能用本地二维码证明成功；close 对静态码只能表达本地关闭；refund 是否支持由原订单插件决定。没有能力时抛 `UnsupportedPaymentOperationException`，支付/退款动作明确被拒绝用 `PaymentDefinitiveException`，已发送但结果不明用 `PaymentUncertainException`。查询失败也属于无法确定支付结果，不能作为支付被拒绝的证据，不据此推进订单失败。

退款的 `pending/unknown` 不是成功，也不会自动重发；新增异步退款插件前须补齐平台查询/回调和结果核对，不能只实现 `refund()` 就认为异步流程完整。当前四个监听插件不支持接口退款，详见[退款申请边界](V1-16-易支付V1接口参考.md#退款申请)。

退款执行边界是进入插件 `refund()`：此前的快照读取和 `init()` 失败属于未执行，记录 `refund_not_executed` 并释放本次额度；进入动作后无法确认的异常保持结果未知。`init()` 只能装配参数，不得在其中发起退款或其他外部写操作。同号重试始终读取原记录，不自动重新调用插件。

插件结果的状态与原因码由现有退款服务一次映射：success → SUCCESS/refund_success，failed → FAILED/refund_failed，pending → PROCESSING/refund_pending，unknown → UNKNOWN/refund_unknown。原请求号、金额、平台退款号及状态字段验证仍在映射前完成；此映射不执行网络请求，也不代替锁内额度和幂等核对。

ACK 采用平台实际要求，不统一套后台 JSON。`notifySuccess(): string|Response` 在相关交易确认后，或明确非入账消息无需确认时调用；ACK 不等于发生收款。`notifyFail(string $message): string|Response` 接收可公开的业务错误说明，由插件决定失败应答格式及状态。服务只向它传递 BusinessException 的公开 message，不传任意 Throwable 原文、SQL 或凭证。服务和控制器原样返回插件应答，不转换为 status/content_type/body 数组；普通正文直接返回字符串，平台确实要求自定义状态或响应头时才返回框架 Response。

当前支付宝手机监听与微信手机/PC 监听直接返回字符串：成功 `200`，业务拒绝 `400：错误原因`，原因最多保留 4000 个 UTF-8 字节；框架使用默认 HTTP 200，不另行调用 response()。通知工具按默认 Accept 或 Accept: text/plain 接收字符串正文；若请求明确使用 Accept: application/json，ThinkPHP 会按原生内容协商将字符串编码为 JSON。正文业务码不能当作 HTTP 状态。程序故障仍走统一异常处理的 5xx；未知通道、配置未成功装配等尚未进入插件应答的入口错误保留原 HTTP 状态。此约定不改变易支付商户通知的 `success` 应答。

## 8. 最小完整骨架

下载[ExamplePayment.php](examples/ExamplePayment.php)。它完整实现基础接口，可用于核对类签名、元信息和动态字段，但所有交易动作明确拒绝，**不是可收款插件**。实现真实协议后再放入正式目录，不能为通过展示而返回假成功。

采集错误的分类用于状态与重试，第三方错误码和说明由插件/SDK 提取并如实传递；公共服务不解释平台协议。可选诊断字段、截断及后台展示规则见[主动采集](V1-25-主动采集与会话协作.md)。登录、解析和验签失败应说明实际阶段，不能统一覆盖为“数据异常”。

验证至少覆盖字段类型、初始化、真实协议认证、金额时间、重复/迟到、批量匹配、异常和重放边界；采集插件再检查单次 200 条上限、账号归并、永久登录态、重启恢复、预登录与重复流水。真实平台验证与合成测试分别记录。

## 9. 易支付 V1 第三方平台插件

`EpayV1Payment` 作为商户对接第三方平台，与本站对业务网站提供的 API 共同遵循[易支付 V1 文档](https://epay.qcjy.cc/doc_old.html)：下单/查询成功 code=1，退款成功 code=0。两个方向的实现和签名类分别位于 `common/sdk/epay` 和 `service/payment/epay`，不因此采用不同协议；移除插件不应删除本站协议签名类。本站错误响应及内部退款状态的区别见[退款申请](V1-16-易支付V1接口参考.md#退款申请)。

1. 安装代码后在“插件管理”刷新目录，启用“易支付 V1”。
2. 新建支付宝或微信通道，选择该插件，填写第三方 `gateway`、`pid`、`key`，选择下单方式 `pay_method`。默认 `submit`（页面支付），可选 `mapi`（API 下单）。网关为 HTTP(S) 根地址或安装子目录，不附加接口文件名、query 或 fragment；支持公网及内网部署，例如 `http://epay.internal:8080/pay/` 或 `http://epay:8080/`。
3. 正常保存并启用通道，通过默认组或自定义路由下单。第三方商户须已开通所选支付方式；本地通道通过配置校验不代表第三方账号已验证。

| 动作 | 第三方接口及规则 |
| --- | --- |
| pay：submit（默认） | 本地生成 MD5 签名的 `submit.php` 链接，由浏览器 GET 进入第三方收银台；不从服务器发起下单请求。out_trade_no 使用本地支付号；此时 channel_order_no 为 NULL，收到成功回调后记录第三方 trade_no |
| pay：mapi（可选） | 服务器 POST `mapi.php`，附带 clientip/device 并签名；`code=1` 仅表示受理。out_trade_no 使用本地支付号；实际返回的 trade_no 写 channel_order_no |
| notify | 共用本地 notify 路由，默认使用支付单号。插件验证原始签名、PID、订单号和 `TRADE_SUCCESS`，核心锁内核对方式、金额和归属后确认 |
| query | GET `api.php?act=order`，使用原 PID/KEY 和 out_trade_no；`code=1` 表示查询成功，`status=1` 才表示付款成功，`endtime` 提供时作为付款时间。code 非 1 抛 PaymentUncertainException，不改变本地支付状态 |
| refund | POST `api.php?act=refund`；act 位于 URL，正文仅提供原 PID/KEY、out_trade_no、money；**`code=0` 才是成功**。须先在第三方后台开启接口退款 |
| close | 文档无关闭接口，插件明确返回不支持；本地关闭不代表第三方订单已撤销 |

SDK 查询、mapi 和退款要求 MPAY 服务器能访问网关；submit 页面支付还要求付款浏览器能访问网关，第三方平台须能访问 MPAY 回调地址。内网 HTTPS 仍需使用受信任且匹配主机名的证书，网络可达不代表支付已经成功。

商品名由本站建单入口在验签后按 UTF-8 截断至 127 字节，插件转发已冻结的 subject，不重复截断。mapi 的 device 来自订单 `_env`：对外 mapi 读取原请求 device（缺省 pc），页面下单使用 UA 识别结果；不是固定填写 pc。平台失败说明共用脱敏及 512 UTF-8 字节限制，查询失败与下单/退款拒绝分别使用对应异常，不新增自动查询或重试入口。

通知支持 GET 或 POST，分别读取实际 URL 查询串或表单，不合并两种输入。必须明确提供 sign_type=MD5，缺失、空值或其他算法均不通过；除 sign/sign_type/空值外的原始字段参与签名，金额先验签后按十进制元字符串转换为整数分。平台重复通知只有在订单身份和金额一致、原通知责任仍存在时应答成功；签名、金额或归属错误不会确认订单。

epay 应答固定为 HTTP 200、纯文本 `success` 或 `fail`。插件返回原生 Response 只为固定正文类型，防止请求 Accept 触发 JSON 编码；公共服务原样透传，不增加 ACK 转换器。未能初始化插件的入口错误、程序或数据库故障仍交统一异常处理。

submit 仅将签名链接交给现有 jump 组件，不公开 KEY，不重复保存整份请求参数；尚未获得平台订单号时不使用本地号占位。mapi 可同时提供多种材料，按 payurl → qrcode → urlscheme 的优先顺序取首个非空值；选中项必须为字符串并通过对应地址或二维码格式检查，不能在选中项无效时悄悄改用另一项。二维码复用现有组件；网页或支付宝/微信唤起地址使用 jump 组件。HTTP(S) 链接在当前页签的原支付单首次展示时自动前往，客户端协议仍由用户点击按钮唤起；返回本站后不重复自动跳出，具体约定见[收银台页面与扩展](V1-30-收银台页面与扩展.md)。第三方回跳只返回本地收银台；订单成功及商户通知完成仍以本站数据库为准。

退款明确拒绝时，插件用 PaymentDefinitiveException 提供已脱敏说明；网络超时、无效 JSON 或无法确认的响应使用 PaymentUncertainException。服务分别通过 payment.refund_rejected / payment.refund_unknown 记录 pay_no、refund_no、plugin_code、reason_code、request_id 及最多 2048 个 UTF-8 字节的 error_message，超长标记截断，不保存完整响应或凭证。诊断日志表达捕获的异常类别，最终持久状态仍按是否进入退款动作及原结果规则决定；不新增公开退款字段，不释放未知退款额度，也不自动重试。

notify 文档不提供付款时间，paid_at 保存首次接收确认时间。query 文档中的 api_trade_no 不从 trade_no 猜造，也不在本插件的通知中写入监听防重字段。epay 不生成 ma_receipt_flow，不占用真实流水记录；金额仍用现有订单金额快照，统计和商户通知继续复用公共生命周期。

epay 不实现 ReceiptCollectorInterface，不预登录、不定时采集，也不增加自动查询/补单任务。submit 只重建原单签名链接，mapi 以同一本地支付号请求上游；中断不生成另一订单号，结果无法判定时保留未知。恢复由普通请求触发，不承诺上游一定幂等；退款结果未知不重发。第三方通知继续确认原单。两个方向的 EpayV1Signer 保持独立。真实平台和资金结果需人工联调，语法及装配检查不等于验收通过。

## 10. SDK 网络与签名边界

SDK 自行确定平台地址和接口路径，固定平台使用自身地址常量，可配置网关由插件及 SDK 按平台规则核验。统一传输调用为 `$http->send($request, $deadline, $maximumBytes)`，其中响应正文上限可省略，默认 64 KiB、最大 4 MiB；可选第四参数为响应头上限，默认 16 KiB、最大 64 KiB。不再创建或传入重复的平台站点允许列表。

公共 `HttpClient::send` 检查实际请求 URL、HTTP(S) 协议及无片段要求，主机解析和连接交给 Guzzle/cURL，不统一要求公网 IP。SDK 可连接配置的私网 IP、localhost、内网域名或单标签主机名，无须开发环境开关或内网放行参数。TLS 证书验证、禁止自动重定向和代理、截止时间、请求及响应大小限制继续保留；签名、响应解析和业务结果由对应 SDK/插件处理。

商户通知在建单时核对应用域名授权，发送时使用 `HttpClient::get`，保留通知端口、每次发送前的 DNS/IP 核验、连接地址绑定和实际 IP 一致性检查。目标仍须使用标准 IP 或完整域名，开发例外沿用明确环境、主机和端口；旧责任按冻结目标发送。SDK 的配置平台地址与接入方提交的商户通知地址分别处理，不增加第三套传输客户端或策略参数。

`HttpTargetPolicy::uri($url, $maximum)` 只检查通用地址格式，主机名使用 PHP 原生规则并允许单标签名称；长度参数不表示已经验签或目标属于公网。原始目标默认上限为 2048，完整请求使用 `MAX_REQUEST_URL_LENGTH`（16384）。商户通知/回跳的 query 由 `UrlEncodedForm::parseQuery` 严格解析并直接用于签名；平台 SDK 的参数遵循自身协议，不套用易支付的字段名限制。

表单和签名 query 的拆分、百分号及加号解码复用已有 `GuzzleHttp\Psr7\Query::parse`（RFC1738）；不使用会改写点号/空格字段名的 `parse_str`。公共薄层继续拒绝重复字段、数组、畸形百分号和无效 UTF-8，并保留字段名及数量限制；裸字段按空字符串处理，空分隔项忽略但仍计入数量，字符串 `0` 保留。签名目标 query 另拒绝点号/空白字段名。编码继续使用 PHP 原生 `http_build_query`，不改写已解码值或对签名参数做 trim。

商户通知和回跳由 `EpayV1MessageService::targetUrl` 统一组装：保留原 URI 的非 query 部分，以已签名参数替换 query，校验实际输出的字段和完整 16384 字符上限。不再解析将被替换的旧 query，通知认领端也不再重新解析完整 URL；冻结载荷的订单身份、签名形态及值类型核验仍保留。建单的早期输入检查、签名准备、冻结数据读取和发送前 DNS/IP 检查各有不同职责，不以删重复为由取消。
