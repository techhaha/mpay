# 支付插件开发

后台表单定义来自已同步的数据库插件目录。单项配置按 code 读取一条记录，与列表共用版本、名称、类名、支持方式、schema 和描述的同步检查；固定代码目录发现仍由工厂负责。插件列表的关联通道数一次按插件编码分组统计，排除已删除通道，不增加持久统计或跨请求缓存。

插件解释平台协议和收款识别，服务负责装配、归属检查及最终生命周期，SDK 负责平台 HTTP、签名和解析。四个主类直接实现接口，不继承公共支付 Base，也不增加 capabilities/source 准入层。

## 1. 放置与发现

主类位于 `app/common/payment/YourPayment.php`，SDK 位于 `app/common/sdk/平台目录`，接口位于 `app/common/interface`。固定目录扫描具体类并拒绝重复插件编码，数据库中的类名不能作为任意执行入口。

插件目录发现时一次核对实现接口、编码及元信息；执行时仍创建独立实例并检查本次实际配置，不复用带账号状态的插件实例。

新增/修改代码后在后台刷新插件目录，核对字段并启用。新插件默认停用；插件代码升级后重启两个常驻命令。只刷新目录不自动重写已有通道配置或旧订单快照。

## 2. 选择实际需要的接口

| 接口 | 用途 |
| --- | --- |
| `PaymentInterface` | 元信息、初始化、重放能力及 pay/query/close/refund |
| `ChannelNotifyInterface` | 继承 PaymentInterface，定义 notify、notifySuccess、notifyFail，处理 HTTP 推送与协议应答 |
| `ReceiptCollectorInterface` | 继承 PaymentInterface，定义 collect、matchReceipts、prelogin 及 isPreloginEnabled，处理整套主动监听 |

支付插件使用这三个合同；收银台展示使用前端组件，不增加后端页面接口。插件同时需要 HTTP 推送和主动查询时可实现两个扩展接口；仅采集的插件不用实现 HTTP 通知或返回占位 ACK。后台通道“接入信息”只为实现通知接口的插件提供回调地址；仅采集插件显示由后台任务查询。

预登录由采集插件的代码元信息 `prelogin` 决定，未声明默认为 false。`isPreloginEnabled(): bool` 读取该声明，工厂发现时核验声明，调度器通过接口直接读取，不根据类名或账号字段猜测。完整输入/输出、声明示例、状态缓存与预算见[主动采集合同](V1-25-主动采集与会话协作.md)。

仅手机推送的插件不实现主动采集接口；没有此接口，watch 不调度它。平台专项诊断放 `tests/diagnostics`，不新增正式守护命令。

## 3. 元信息、配置与实例

提供唯一 code、名称、版本、支持的支付方式、可选纯文本 description 和 `config_schema`。`$paymentInfo` 是代码声明，不是订单或真实账号信息。字段规则见[完整 schema 合同](V1-24-config-schema字段规则.md)。

元信息通过接口方法返回；下表约束由 `PluginDefinition` 和插件目录发现流程检查，不是通道配置值：

| 方法 / 元信息 | 类型与约束 | 示例或用途 |
| --- | --- | --- |
| `getCode()` / code | 1～64 个 ASCII 字符；小写字母开头，后续只能是小写字母、数字或下划线；全目录唯一 | `example_receipt`；不能使用中文、连字符或类路径 |
| `getVersion()` / version | 1～32 个 ASCII 字符；字母或数字开头，后续可含字母、数字、下划线、点和连字符 | `1.0.0`、`1.1.0-beta`；用于展示和记录，不负责选择多份代码或限制启用 |
| `getName()` / name | 非空字符串 | 后台显示名称，例如“示例收款” |
| `getEnabledPayTypes()` / pay_types | 非空列表；每项为 1～32 个 ASCII 字符，小写字母开头，后续只能是小写字母、数字或下划线 | `['alipay', 'wxpay']`；这里声明支持范围，方式是否存在、启用仍由目录和选路检查 |
| `getDescription()` / description | UTF-8 纯文本，最多 8192 字节；无说明时返回空字符串 | 不返回 HTML；空说明不显示说明区 |
| `getConfigSchema()` / config_schema | 有序字段列表，最多 128 项 | 属性、默认值与校验规则见字段规则文档；无参数时返回 `[]` |

上述方法及 `canRetryPay(): bool` 必须在 `init()` 之前可读取，不依赖通道账号。主动采集插件另提供 `isPreloginEnabled(): bool`；未声明预登录时返回 false，具体合同见[主动采集](V1-25-主动采集与会话协作.md#5-登录状态与预登录)。

单订单动作创建独立实例并 `init(array $channelConfig)`；批量采集/匹配直接使用 orders/channels 输入，不依赖上一次单通道 init 的残留设置。输入包含原版本插件设置，以及服务提供的 channel_id、api_config_id、receipt_scope_key 等运行字段；不能允许请求覆盖这些保留字段，也不序列化给前端或日志。

单订单的下单、回调和退款统一通过 PaymentPluginFactoryService::initialize 校验配置、核对参数冲突并调用 init。init 只装配参数，不发起支付或其他外部写操作；pay 在执行认领提交后调用。下单的 upload 派生地址在准备阶段装配，回调和退款不依赖二维码图片文件。元信息按类缓存，执行实例保持独立；代码更新后重启常驻进程。

支付方式使用通用编码规则，实际是否允许新单由目录、插件支持及选路决定；内部建单对象不写死支付宝、微信名单。

## 4. pay 输入

```php
[
    'pay_no' => 'P2026100915304505189',
    'biz_no' => 'B2026100915304512345',
    'pay_type_code' => 'alipay',
    'amount' => 1234, // 原业务金额，整数分
    'expire_at' => '2026-10-09 15:35:45', // 上海时间
    'extra' => [],
]
```

`canRetryPay()` 在初始化之前也必须可读。仅无外部副作用或平台严格按原单幂等时返回 true，不能因为“多数时候成功”就允许重放。pay() 由下单请求或收银台准备请求调用；后台 payment:work 不扫描或恢复付款准备。重复请求复用已保存材料，未完成执行仍受原单认领和安全重试约束，不能重新分配已保存金额或备注。

## 5. 当前静态码结果

`pay()` 返回 `pending` 时，下列键都必须提供。可空表示明确返回 `null`，不是省略该键，也不是返回空字符串。

| 字段 | 类型与约束 | 含义 |
| --- | --- | --- |
| status | 字符串 `pending` | 付款材料已准备，不代表到账 |
| pay_no | 原输入支付号字符串；边界校验最长 64 字符，当前系统生成 20 位 | 原样返回，不自行生成或替换 |
| paid_amount | `null` | 尚未确认业务支付金额 |
| chan_order_no / chan_trade_no | 各为 `null` 或非空字符串，最多 128 字节 | 有真实平台编号才填写；静态码准备阶段通常为 null |
| pay_type | 支付方式编码，沿用原输入 `pay_type_code` | 1～32 个 ASCII 字符，语法同元信息中的支付方式 |
| pay_product / pay_action | 各为 1～64 个 ASCII 字符，字母开头，后续只能是字母、数字或下划线 | 分别记录插件实际使用的产品和动作，例如 `alipay_qrcode` / `display_qrcode`，不是中文标签或 URL |
| presentation | 仅含 `pay_page`、`pay_params` 的关联数组 | 页面标识、公开参数类型和大小见[展示字段约束](V1-30-收银台页面与扩展.md#展示字段约束) |

`pay_product` 和 `pay_action` 是插件声明的产品与动作标识，用于追踪本次付款准备路径，不由服务根据插件名或页面反推。插件有多个产品/动作时，按实际执行分支填写；它们不作为支付成功证据，也不混入后续采集的查询接口名称。当前静态码插件没有在 pay() 中请求平台下单，具体值如下：

| 插件及实际分支 | pay_product | pay_action | 动作含义 |
| --- | --- | --- | --- |
| 支付宝手机收款监听 | alipay_qrcode | display_qrcode | 展示支付宝收款码 |
| 微信手机/PC 收款监听 | wechat_qrcode | display_qrcode | 展示微信收款码 |
| 收钱吧码牌流水 | shouqianba_qrcode | display_qrcode | 展示收钱吧收款码 |
| 支付宝账单：金额/手动备注 | alipay_qrcode | display_qrcode | 展示支付宝收款码 |
| 支付宝账单：自动金额和备注 | alipay_transfer | create_transfer_link | 生成支付宝客户端转账入口，供付款人操作 |

这些是当前插件定义的标识，不是核心的产品白名单。服务只校验通用格式并随 presentation 保存。后台“订单详情 → 处理记录 → 技术信息”读取原单的两个值；未完成材料准备时显示“—”，不读取当前配置补写。生成转账入口不表示已调用平台资金划转接口。

若 `pay()` 已取得真实成功证据，可返回 `success` 并按下一节提供原业务金额和标准流水；仍须提供 `chan_order_no/chan_trade_no` 两个可空键，此时不再要求 presentation。不能用二维码、受理成功或页面跳转替代收款证据。当前四个监听插件准备付款材料时均返回 pending。

```php
[
    'status' => 'pending',
    'pay_no' => $order['pay_no'],
    'paid_amount' => null,
    'chan_order_no' => null,
    'chan_trade_no' => null,
    'pay_type' => $order['pay_type_code'],
    'pay_product' => 'alipay_qrcode',
    'pay_action' => 'display_qrcode',
    'presentation' => [
        'pay_page' => 'page',
        'pay_params' => [
            '_page' => 'receiptQrcode',
            'qrcode_content' => $qrText,
            'qrcode_image_url' => $verifiedLocalImageUrl,
            'instruction' => 'manual_remark', // 普通扫码用 scan，并令 remark=null
            'remark' => $preparedRemark,
        ],
    ],
]
```

这是假设已经完成识别值准备的结果形状。插件生成并校验具体公开材料，服务校验通用结构后保存 presentation 快照。前端当前注册 receiptQrcode 和 alipayTransfer；新增页面实现并注册前端组件，公共后端不需要配套增加平台展示类，不接受任意模板路径。金额、备注与有效期从本单冻结事实生成，页面只显示一处应付金额。pay_params 只能放插件明确挑选的公开 JSON，不得直接返回配置、整个 ext_json 或上游原文；服务不会猜测并删除其中的秘密字段。倒计时读取公共 order.expires_at/server_time，不在每个页面参数中注入时间或二维码编码规格。扩展步骤见[收银台页面与扩展](V1-30-收银台页面与扩展.md)。

现有监听插件在自己的短事务中按 BizOrder → PayOrder → PaymentChannel 顺序加锁，再按 channel_id 分页读取有效待付订单快照。无准备快照的初始化金额不占用识别值，完整快照直接复用，部分损坏的快照拒绝重新分配。金额模式保持通道内金额唯一；备注模式分配通道内唯一四位备注，同时必须核对金额。同一通道跨应用共同占用，不同通道互不占用。模式切换仍尊重旧单快照，不能新增与旧金额识别单同额的备注订单。

订单本身保存准备事实，不建立识别预约表，不依赖缓存来保证唯一。插件决定金额、备注及付款窗口，服务校验标准金额、原单归属和重复流水，再统一提交交易。服务派发插件时不持有外部 HTTP 事务；新插件不能把平台请求放进可重试数据库闭包。

当前四个监听插件在 `ext_json.personal_receipt` 保存 `original_amount`、`receipt_amount`、`match_mode` 和 `remark`。金额均为整数分；偏移展示由 `receipt_amount - original_amount` 计算，不额外保存 `offset_amount`。到账后由生命周期补充实际收款证据，插件返回的公开付款参数仍与内部快照分开。

## 6. notify 与整批匹配

认证并解释平台记录后返回：

```php
[
    'status' => 'success',
    'pay_no' => $matchedPayNo,
    'paid_amount' => $originalAmountInCents,
    'chan_order_no' => $platformTradeNo,
    'chan_trade_no' => $platformTradeNo,
    'receipt' => [
        'pay_type' => 'alipay',
        'event_key' => $stableEventKey,
        'trade_no' => $platformTradeNo,
        'amount' => $receivedAmountInCents,
        'paid_at' => $paidAt,
        'remark' => $payerRemark,
    ],
]
```

这是插件识别结果，还没有完成数据库确认。插件不在 notify 中提前恢复金额或预写最终流水；服务核验证据后通过生命周期统一提交。事件键稳定、实际收款金额和平台号真实，缺失可空字段不伪造。

成功结果的 `status` 固定为 `success`，`pay_no` 必须引用原订单；`paid_amount` 是原业务金额的整数分，必须与原单一致。`receipt.amount` 是实际到账的整数分，两者不能混填。`chan_trade_no` 应与 `receipt.trade_no` 一致；付款时间统一放在 `receipt.paid_at`，成功结果外层不再返回重复的 `paid_at`。

### 标准流水字段

HTTP 通知结果中的 `receipt`、主动采集的 `records` 元素，以及 `matchReceipts()` 返回的流水证据共用下表。前六个键必须存在；可空字段没有可靠来源时填 `null`，不能省略或用空字符串代替。文本须为有效 UTF-8；“字节”与“字符”分别按表中单位判断。

| 字段 | 类型 / 可空 | 约束与含义 |
| --- | --- | --- |
| pay_type | string，不可空 | 支付方式编码，1～32 个 ASCII 字符，小写字母开头，后续只能是小写字母、数字或下划线；须与原单方式一致 |
| event_key | string，不可空 | 非空，最多 128 字节；同插件范围内稳定唯一，同一条流水重试时不得改号，不包含认证凭证 |
| trade_no | string 或 null | 非空时最多 128 字节；有可靠平台交易号或既定监听协议编号才提供，不能伪造平台交易号 |
| amount | int，不可空 | 实际到账金额，1～999999999 分；不接受数字字符串或浮点数，并须匹配本单识别金额 |
| paid_at | string 或 null | 上海时间 `Y-m-d H:i:s`，严格的 19 字符有效日期时间；实际自动匹配还须有可靠时间并落在原单付款窗口内 |
| remark | string 或 null | 非空时最多 256 个 UTF-8 字符；是否必需以及如何解析由插件的匹配方式决定 |
| extra | array，可省略，不接受 null | 脱敏的平台补充信息；使用 `JSON_UNESCAPED_UNICODE` 编码后最多 4096 字节，JSON 编码深度上限 16；不能带认证状态或完整原始响应 |

标准流水不接收未声明的顶层字段。服务会根据标准字段及 extra 重新计算 `payload_digest`，插件无需生成或依赖自己传入的摘要。流水备注的 256 **字符**限制与收银台组件 `remark` 的 256 **字节**展示限制用途不同，不能直接视为同一个边界。

稳定事件键是插件开发要求，不能把每次 HTTP 请求的新时间或随机值当作新的真实流水。当前手机兼容适配仍将请求 timestamp 纳入监听编号，改变请求时间的重发不能保证同键去重；其时间语义与现有限制见[手机重发与时间的当前限制](V1-11-微信手机与PC监听.md#手机重发与时间的当前限制)。不要将该限制复制成新插件的推荐实现，也不要据通用幂等约束宣称当前手机路径已解决所有重发情况。

`matchReceipts($receipts, $orders, $channels)` 接收本次单页响应的整个 `list<{record,consumed_pay_no}>` 批次及对应原单/通道版本，返回逐笔匹配结果；未匹配不返回，同批不重复选择同一订单。一条流水只消费一次。手机在明确通道内保留单候选规则；账单/码牌先按通道区分候选，再按付款窗口和距发起时间选择，等距稳定排序。相同真实账号可以合并登录和查单，但一条流水若符合多个通道候选，则跳过并记录 ambiguous_channel，不能按通道遍历顺序分配。

四个内置插件均保留金额与手动备注模式；备注能否自动识别取决于实际消息或平台流水是否提供备注，不能猜测缺失值。支付宝账单另提供 alipay_transfer 模式：插件生成携带同一金额和备注的二维码及手机入口，公开页面为 alipayTransfer；最终仍由账单采集按备注＋金额确认，不因打开链接而成功。收钱吧保留付款端输入金额及备注的流程。

## 7. 其他动作与失败语义

query 不能用本地二维码证明成功；close 对静态码只能表达本地关闭；refund 是否支持由原订单插件决定。没有能力时抛 `UnsupportedPaymentOperationException`，明确拒绝用 `PaymentDefinitiveException`，已发送但结果不明用 `PaymentUncertainException`。

退款的 `pending/unknown` 不是成功，也不会自动重发；新增异步退款插件前须补齐平台查询/回调和结果核对，不能只实现 `refund()` 就认为异步流程完整。当前四个监听插件不支持接口退款，详见[退款申请边界](V1-16-易支付V1接口参考.md#退款申请)。

退款执行边界是进入插件 `refund()`：此前的快照读取、配置校验和 `init()` 失败属于未执行，记录 `refund_not_executed` 并释放本次额度；进入动作后无法确认的异常保持结果未知。`init()` 只能装配参数，不得在其中发起退款或其他外部写操作。同号重试始终读取原记录，不自动重新调用插件。

ACK 采用平台实际要求，不统一套后台 JSON。`notifySuccess(): string|Response` 在交易确认后调用；`notifyFail(string $message): string|Response` 接收可公开的业务错误说明，由插件决定失败应答格式及状态。服务只向它传递 BusinessException 的公开 message，不传任意 Throwable 原文、SQL 或凭证。服务和控制器原样返回插件应答，不转换为 status/content_type/body 数组；普通正文直接返回字符串，平台确实要求自定义状态或响应头时才返回框架 Response。

当前支付宝手机监听与微信手机/PC 监听直接返回字符串：成功 `200`，业务拒绝 `400：错误原因`，原因最多保留 4000 个 UTF-8 字节；框架使用默认 HTTP 200，不另行调用 response()。通知工具按默认 Accept 或 Accept: text/plain 接收字符串正文；若请求明确使用 Accept: application/json，ThinkPHP 会按原生内容协商将字符串编码为 JSON。正文业务码不能当作 HTTP 状态。程序故障仍走统一异常处理的 5xx；未知通道、配置未成功装配等尚未进入插件应答的入口错误保留原 HTTP 状态。此约定不改变易支付商户通知的 `success` 应答。

## 8. 最小完整骨架

下载[ExamplePayment.php](examples/ExamplePayment.php)。它完整实现基础接口，可用于核对类签名、元信息和动态字段，但所有交易动作明确拒绝，**不是可收款插件**。实现真实协议后再放入正式目录，不能为通过展示而返回假成功。

采集错误的分类用于状态与重试，第三方错误码和说明由插件/SDK 提取并如实传递；公共服务不解释平台协议。可选诊断字段、截断及后台展示规则见[主动采集](V1-25-主动采集与会话协作.md)。登录、解析和验签失败应说明实际阶段，不能统一覆盖为“数据异常”。

验证至少覆盖字段类型、初始化、真实协议认证、金额时间、重复/迟到、批量匹配、异常和重放边界；采集插件再检查单次 200 条上限、账号归并、永久登录态、重启恢复、预登录与重复流水。真实平台验证与合成测试分别记录。
