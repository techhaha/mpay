# 版本更新与文档维护

本页说明已有站点如何核对版本、安排更新，以及文档如何与代码一起维护。全新安装请看[网页安装](V1-03-安装与环境要求.md)，换服务器或恢复备份请看[备份恢复](V1-19-备份恢复与域名迁移.md)。

## 先分清你要做哪件事

| 目标 | 应使用的流程 |
| --- | --- |
| 新建一个没有业务数据的站点 | 使用对应版本程序和专用空库，完成网页安装 |
| 已有站点更新代码 | 先确认目标版本的升级说明适用，再按下方顺序操作 |
| 换服务器、换域名或恢复备份 | 恢复配套程序、数据库、配置和图片，不重新安装 |
| 只更新在线文档 | 发布文档副本，不会自动更新任何站点或已经下载的安装包 |

在线 Wiki 跟随 `v1` 分支维护，发行包可能早于当前源码。排查前先记录自己使用的发行版本或源码提交号，不要仅凭文件夹名称判断版本。

## 更新程序

**当前安装器只负责固定基线的新装及中断续装，没有旧版数据库的通用自动升级入口。** 未找到适用于当前版本的升级说明时，先保留原站点和备份，请维护人员核对；不要通过重跑 `/install`、删除安装记录或清库来尝试升级。

确认存在适用的更新路径后，按顺序操作：

1. 阅读目标版本的发行说明，核对 PHP、依赖、数据库变化及已安装插件的接口要求。
2. 按[备份步骤](V1-19-备份恢复与域名迁移.md#使用面板时怎么操作)保存同一时点的程序、数据库、`.env`、`runtime/install.lock` 和上传图片。
3. 暂停本站访问及收款入口，停止本站的 `payment_watch`、`payment_work`，确认没有另一套进程继续处理相同订单。
4. 更新目标版本的程序及配套依赖，保留原 `.env`、安装锁、上传图片和运行数据。源码部署使用 `composer.lock` 安装依赖，不执行 `composer update`，不从其他版本拼接 vendor。
5. 数据库只执行该版本明确提供的升级步骤。没有结构变化时，不要额外运行新装命令或修改安装进度。
6. 检查网站与命令行 PHP；在后台核对原应用、通道、收款图片、订单和通知记录。插件定义有变化时刷新“插件管理”，按表单提示核对配置。
7. 按[后台任务教程](V1-18-部署与后台任务.md)以网站运行用户启动两个任务，更新 PHP 扩展时同时重启对应 PHP 服务；检查 RUNNING、日志和近期活动。
8. 恢复站点访问，核对停机期间的原订单和通知，再按[第一笔收款](V1-04-完成第一笔收款.md)验证新订单。停机后不能假设所有历史账单都会自动补齐。

更新结果不明时先保全当前状态。备份之后若已有新到账或已发出通知，直接恢复旧数据库会丢失新记录，应先核对原订单再确定恢复办法。

## 数据库结构变化与更新边界

当前结构以[数据库字段字典](V1-27-数据库表与字段字典.md)和对应版本建表定义为准。新装基线为 `202610140100_install`，名称相同不代表文件内容、SQL 摘要或已有库结构相同。

较早的开发结构曾清理以下字段，维护旧安装时需单独核对：

| 表 | 已移除字段 | 当前保留的内容 |
| --- | --- | --- |
| ma_payment_channel_revision | snapshot_digest | 冻结快照正文、配置版本及订单关联 |
| ma_notify_task | lease_owner | 当前发送令牌、租约时间及尝试状态 |
| ma_notify_attempt | response_digest | 商户响应片段、HTTP 状态、结果及截断标记 |
| ma_receipt_flow | remark、evidence_json.source_payload_digest | 成功绑定、真实交易号、金额、必填付款时间及稳定交易摘要；原文统一取 notify.raw 写回调记录 |

订单 `personal_receipt` 中的付款时间和渠道交易号使用正式列，不重复维护 `notified_at`、`channel_trade_no` JSON 键。这些是结构核对信息，**不是可以直接照抄执行的删除清单**；已有数据须先核对来源、备份及目标版本的处理方案。

已安装版本对应 SQL 的原始字节必须保留。当前基线使用 CRLF；上传工具或编辑器转换换行也可能导致安装进度核对失败。不要手工改摘要或删除记录，按[安装中断与提示](V1-03-安装与环境要求.md#安装中断与常见提示)核对原文件及技术日志。

2026-10-28 开发基线统一收款回调：重定义 ma_pay_callback_log、退役 ma_channel_notify_log、订单操作审计允许系统操作者，保留成功流水表和交易事实。共 24 张业务表，管理操作请求号索引一并保留。已有环境须明确授权后先备份、核对并对齐真实结构及安装记录；没有历史兼容或自动转换入口，不能只覆盖 SQL 或改摘要。

notify 当前合同统一为十个平级字段，不读取旧 receipt 结构。paid_at 非空，业务订单引用稳定，真实流水号缺失保持 NULL；实收与原业务金额仍分开。现有库更新须在停止旧进程并备份后显式对齐字段、摘要和安装记录，同时保留订单、金额、付款时间、退款及通知事实；不能让旧插件与新服务混用，也不重建历史日志的原文。

## 文档怎么跟随版本

README 是项目入口，`docs/wiki/` 是公开正文的维护源，远程 Wiki 是发布副本。本站 `/docs/` 从接口参考生成，不能单独手改生成页面。

| 内容 | 维护位置 |
| --- | --- |
| 项目介绍、能力概览、开始使用入口 | 根目录 README.md |
| 点哪里、填什么、完成后检查什么 | 对应安装、配置或日常操作教程 |
| 常见故障的快速定位 | 常见问题表；完整解决办法放在所属专题，并给出直达链接 |
| API 字段、签名和可复制示例 | 易支付接口参考及 examples/，同步生成本站文档 |
| 插件接口、配置字段、采集和展示规则 | 对应开发参考章节；使用教程只链接需要的内容 |
| 逐次发布变化和实际验证结果 | 对应发行说明与 Git 记录，不反复追加到所有教程末尾 |

每次修改先检查内容归属，再按以下顺序更新：

1. 先改主题所在的完整说明，保留必要的操作步骤和解决办法；正文描述当前行为，历史差异放在更新说明。
2. 检查 README、导航、相关概览和示例是否与正文一致。相同规则尽量集中维护，必要的摘要不能代替具体操作。
3. 面向用户的教程使用界面上的实际名称，按“准备 → 操作 → 完成检查 → 失败处理”组织；代码、锁、事务等内部细节放开发章节。
4. 不用“目前四个插件”“本轮新增”等容易过时的表达；需要列举支持范围时维护明确列表。没有真实平台验证时不编写通过结论。
5. 保留仍被链接的文件名和章节锚点；调整标题或移动章节后检查引用。截图只用演示资料，示例不含真实密钥。
6. 运行文档检查；接口参考变化时重新生成本站文档，按[发布工具说明](tools/README.md)核对产物。提交、推送和远程 Wiki 发布按当次授权分别执行。

使用历史版本时：源码包中的 `docs/wiki/` 可离线阅读；纯净安装包先看包内 README，再到源码仓库选择对应标签或提交查看文档。入口为 [Gitee v1](https://gitee.com/technical-laohu/mpay/tree/v1/) 和 [GitHub v1](https://github.com/techhaha/mpay/tree/v1)，不要依赖仓库默认打开的分支。

## 公共版与本地插件版的开发维护

维护源码时，公共 `v1` 与本地 `codex/dynamic-receipt-plugins` 使用同一 Git 仓库的两个工作树，分别在各自目录开发。它们共享提交、分支和历史，各自保留工作区及暂存区；文件修改不会即时联动，只有已提交的公共更新才能通过合并进入插件分支。

- 公共代码、公共 SDK 和全部共同文档在 `v1` 工作树维护，按授权独立提交后，单向合入本地插件分支。不在两个目录分别修改或复制覆盖同一份公共文档。
- 插件分支维护五款动态码 PHP 入口及整个私有 `premium_sdk/` 源码/构建目录；当前路径及旧十份专属源码的历史路径都不能进入公共 `v1` 的提交树或可达历史。插件分支不设置远程上游，也不推送到任何远程仓库，不整体反向合入 `v1`。
- 完成本地合并后，共同文件应一致，差异只保留专属入口、SDK 私有目录、根 Composer 的源码开发映射及旧平台 SDK 删除；尚未提交的公共修改不属于已同步内容。插件用法、配置字段和扩展要求仍在[动态码插件说明](V1-34-动态码收款插件.md)公开维护。
- 编辑器提示分支已在另一工作树签出时，打开该工作树即可，无需强制切换；本地插件分支不使用“发布 Branch”。本地合并、公共仓库推送、Wiki 发布和测试服部署是不同操作，分别遵守当次授权范围。

这种目录划分是源码维护方式，不改变客户安装步骤，也不要求同时运行两套后台任务。更新文档不等于已经提交 Git、合入插件分支或发布远程 Wiki。
