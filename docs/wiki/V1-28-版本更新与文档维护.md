# 版本更新与文档维护

本 Wiki 对应 `v1` 分支的 ThinkPHP 重构版。旧版发行包、V2 Webman 与当前结构不同，不提供把旧表直接覆盖为新表的兼容安装方式。

## 插件合同更新（2026-10-21）

退款统一按 POST `/api.php?act=refund` 接入；epay 插件把 act 放到 URL，正文只传原凭证、订单号和金额。本站在进入退款服务前拒绝 GET 退款，返回 HTTP 405、Allow: POST 和 code=-1，查询仍支持 GET/POST。成功 code=0 及内部退款状态不变。

退款服务将插件结果的状态与原因码合并为一次映射；拒绝及未知异常共用有界脱敏诊断，分别记录 payment.refund_rejected / payment.refund_unknown。金额、应用归属、幂等认领、事务外平台调用和锁内回写保持，未知结果继续占用额度且不自动重发，没有新增数据库字段或重试任务。

到账确认未通过时，HTTP、采集和 pay 成功结果的共用入口保留核心原因码到现有技术日志，不保存未匹配流水。epay 回调必须明确提供 sign_type=MD5；通知责任创建复用成功消息入口核对双单状态和关联，未提供通知地址也先检查，随后不建任务。原交易锁、唯一约束、通知冻结签名、事务外发送、租约回写和首次有效 ACK 保持。

chan_order_no 继续保留：pay/notify 标准结果中该字段缺失、null 或空串时使用 chan_trade_no，已有值不覆盖，不反向补造交易号。监听字段不删，普通平台确认补缺后仍需有效订单引用。没有数据库结构调整、历史数据回填或新增重试机制。

页面识别环境参数统一为 detectedDevice；mapi 传 null，实际 device 仍从请求读取，缺省 pc。签名格式检查集中在 signer，商品名只在验签后的建单入口截断；插件转发冻结值。单笔与列表共用纯订单字段，code/msg 只保留在响应外层。

手机/PC 监听合成编号仅作为 event_key，未取得真实平台交易号时 trade_no/channel_trade_no 为 NULL，api_trade_no 不以新生成的监听编号填充。仍按原事件键、摘要、金额及归属确认，删除监听插件不再使用的交易号查单分支。平台 query 非成功码抛 PaymentUncertainException，不将查询失败视为支付被拒绝；未新增自动查单、重试、表列或兼容层。此调整不回填历史数据，也不改写已登记的新装 SQL 摘要；旧监听流水重投仍须通过原证据核对，不承诺跨合同格式兼容。

对外 V1 退款响应按协议修正为已确认成功 `code=0`，其他处理结果、业务失败和异常为 `code=-1`。`/api.php` 查询成功仍为 `1`，其失败也统一为 `-1`，覆盖参数解析前的限流及故障，避免误报退款成功；`/mapi.php` 保持成功 `1`、失败 `0`。内部退款状态、额度占用、幂等、未知结果处理及数据库结构不变；接入程序应按操作识别成功码，详见[接口参考](V1-16-易支付V1接口参考.md)。

付款准备遇到确定拒绝或结果未知时，复用既有 SafeLogger 保存有界脱敏诊断，按支付号、通道及插件定位原因；生命周期状态与原异常分类保持，未增加数据库字段、日志框架或重试机制。配置字段规则统一为 init 只接收配置、动作参数另行传递，删除旧的运行字段注入和保留字段说明。

URL/query 处理进一步复用现有 PHP/Guzzle：签名表单使用已有 Query::parse 负责拆分和 RFC1738 解码，项目只补充重复字段、标量、UTF-8、字段名及数量等协议约束；不新增依赖或解析框架。通知/回跳统一在最终地址组装处核验实际 query 和完整长度，删除对被替换原 query 的重复解析，以及通知认领端对完整 URL 的重复解析。签名内容及算法、冻结载荷身份、通知租约、金额/归属与商户网络限制保持；不重新签名旧通知，不新增数据库字段或兼容层。

网络边界按入口区分：商户通知保留域名授权、端口、DNS/IP、公网网段及连接绑定；插件 SDK 不再统一强制公网，直接连接配置的平台地址，支持私网 IP、localhost、内网域名及单标签主机名。共用传输继续验证 TLS、限制截止和大小、禁止自动重定向及代理，不新增白名单模式、内网开关或策略类。通用主机名检查使用 PHP 原生规则，HttpClient 移除不再使用的直接解析器依赖。util 的闲置 Money::add 及对应旧断言退役，其余金额、编号、签名解析、进程锁、文件及日志边界保留；相关 use 导入统一。

采集通知的内部批次改为 records/orders：订单候选复用本轮调度只读快照，并限定账号批次覆盖版本；不再按流水时间扩大查询或在每个通道重复读取同一批订单。context 仍只有通道 ID 和可选支付号，跨通道歧义及锁内逐笔确认保留。mapi 按 payurl、qrcode、urlscheme 的顺序选首个非空材料并校验；HTTP 回调避免逐笔与外层重复记录同一错误，退款明确拒绝说明进入有界脱敏技术日志。submit 的 HTTP 方法准入统一由路由处理，控制器保留解析 query/POST 所需的方法分支；相关 use 导入归一化。没有新增表列、兼容分支或运行机制。

PayPluginInterface 和薄 BasePayment 统一元信息及配置保存；PaymentInterface 合并通知，所有 notify 返回标准结果列表，主动采集按通道初始化后整批投递并逐笔确认。原独立通知接口、独立匹配方法及付款重放开关已退役，不提供运行时兼容。

init 只装配配置，配置值在保存和启用时校验；订单、通道、上传资产地址和环境由动作参数传递。_env/_submit_type 平级，submit 自动识别设备，mapi 严格枚举校验。更新后刷新插件目录并重启常驻命令；现有参数不被刷新改写，缺少提交来源的旧开发订单不补造信息，可重新创建订单使用新合同。原订单到账确认、查询及已保存材料不因此改写。

本次无新表列。退役 JSON 键可在备份后定向删除，不能删除执行令牌、付款窗口或交易证据；具体环境处理及验证记录见项目维护资料。

平台 SDK 的 HTTP 调用同步简化为 `send($request, $deadline, ...)`，删除重复的平台站点策略参数。平台地址及接口规则由插件/SDK 负责，公共 URL 格式、TLS、重定向、超时和大小限制继续执行；DNS/IP 网段检查及连接绑定仅用于商户通知。自定义 SDK 或本地 HTTP 替身须同步新签名，见[插件开发](V1-23-支付插件开发.md)。

URL 通用格式与商户签名 query 检查已分开，应用允许域名改为方法参数；通知发送前一次取得 URI 和已核验地址，不再重复检查字面 IP 或计算开发例外。原公网网段、TLS、DNS 绑定、响应限制及错误处理边界继续保留，旧通知使用冻结目标。相关开发调用需同步新的 URI/目标校验签名，见[插件开发](V1-23-支付插件开发.md)和[商户通知](V1-10-商户通知与人工处理.md)。

### 插件与后台接口变化

- 带流水的成功结果只使用 `receipt.paid_at`，不重复返回外层时间；不带流水的平台订单确认使用外层 paid_at，未提供平台时间时为 null。产品/动作由插件按实际付款准备分支声明，字段与示例见[插件开发](V1-23-支付插件开发.md)。
- 主动采集输入移除未使用的 `current_config_version`；后台采集摘要不再提供推算的 `next_run_at`，连续失败统计使用 `consecutive_failures`，含义为连续失败批次。账号登录态、查询间隔和重试等待仍由插件维护。
- HTTP 回调日志使用单个可空的 `flow_id`，不再提供 `flow_ids`、关联流水计数及对应分页接口。二次开发的后台页面或接口调用方应同步调整。
- 单个插件配置按编码读取数据库定义，保留与本地代码的同步检查；插件列表一次统计关联通道数。配置保存复用事务中已锁定的模型，易支付单项查询复用已读支付单。
- 付款确认只在支付单正式列保存付款时间和渠道交易号，清理 `ext_json.personal_receipt.notified_at`、`ext_json.personal_receipt.channel_trade_no` 两个重复键；金额证据、流水身份与锁内核验保留。收钱吧复用本批轮转读取，凭证候选仅保存摘要到密码的映射；通知过期候选满额后不再追加无效查询。
- 插件缺失清理只判断通道、配置或订单引用是否存在，不再统计全部引用数量；已软删除通道和历史订单仍能阻止删除。通道列表查询不再读取未展示的内部范围字段，其他内部范围用途不变。
- 后台通道列表及详情不再返回未消费的 `scope_key`，详情的 `notification` 不再返回 `method`；通知地址及模式保留。内部收款范围、到账流水的范围展示与回调 POST 协议不变。这组读取精简没有数据库结构变更，不覆盖下文此前字段清理的更新边界。

已有站点应先备份并核对原程序版本、数据库结构及安装进度，确认目标版本提供适用的升级方案后再更新。不要只覆盖 PHP 文件，也不要手动删除字段、修改安装摘要、重跑 `/install` 或清库来绕过检查。当前公开源码未提供旧库到这一结构的通用自动升级入口；一次文档同步也不会更新已下载的安装包。

## 更新程序

当前交付的是纯净新装基线，只用于空库安装，未提供旧开发库到该基线的升级路径。已有站点不能直接覆盖程序后执行 `system:migrate`、重跑 `/install` 或删除安装进度表来完成升级；先确认目标版本明确提供的升级说明。以下是有适用升级路径时的操作顺序。

判断某个站点是否已经对齐版本，应读取该站点当前的表结构、安装记录和程序版本。历史部署日志只能说明当时情况；一次性、明确授权的开发环境基线整理，也不等于程序已经提供自动升级能力。不同环境分别核对，源码同步不应覆盖目标站点的账号、密钥和交易数据。

1. 阅读目标版本明确提供的升级路径，确认适用于当前安装版本。
2. 按[备份指南](V1-19-备份恢复与域名迁移.md)保存一致备份，记录代码、锁文件、数据库与图片的对应关系。
3. 进入维护状态，停止 watch/work，保留原 `.env`、安装锁和上传文件。
4. 部署对应源码及锁定依赖；仅执行该版本明确声明的迁移，不修改已执行 SQL 摘要，也不删除旧迁移记录。
5. 检查网站、命令行环境、数据库及原待办，再恢复两个守护进程。

更新失败不能一律用旧库覆盖，因为新到账和已发送通知可能已经发生。先保全当前状态、核对副作用，再按恢复方案处理。

## 文档怎么跟随版本

README 是产品入口，`docs/wiki/` 是对外正文的唯一源文件，远程 Wiki 是发布副本。每次改接口、配置字段、默认值、状态或后台操作，应同步对应教程和示例。

在线 Wiki 跟随 V1 当前源码更新。使用较早版本时，应阅读与程序对应版本的文档，避免把新界面的按钮或插件接口直接套到旧程序上：

- 源码包保留 `docs/wiki/`，可直接离线阅读同版本正文和图片。
- 纯净安装包不含 `docs/`，先阅读包内 README；再依据下载时记录的版本或源码提交号，在源码仓库选择对应版本查看 `docs/wiki/`，不要默认最新 Wiki 适用于旧包。

两端源码入口为 [Gitee v1](https://gitee.com/technical-laohu/mpay/tree/v1/) 和 [GitHub v1](https://github.com/techhaha/mpay/tree/v1)，当前默认分支均为 `v1`；查看历史链接或下载旧包时仍须核对版本。源码与远程 Wiki 分别保存 Git 历史，文档已更新不代表站点程序或已下载的安装包也已更新。

文档截图使用当前界面和明确的演示数据，不把截图中的金额/状态作为真实平台已验收的证据。接口示例不用真实 KEY 或账号；未知的平台版本明确写明待核对，不补造“通用规则”。

开发者可运行 `python docs/wiki/tools/wiki.py check` 检查本地链接和图片。同步工具的使用见[发布工具说明](tools/README.md)；默认只检查，写出发布目录需要显式参数，工具本身不提交或推送 Git。
