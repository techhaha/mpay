# 版本更新与文档维护

本 Wiki 对应 `v1` 分支的 ThinkPHP 重构版。旧版发行包、V2 Webman 与当前结构不同，不提供把旧表直接覆盖为新表的兼容安装方式。

## 近期功能变化（2026-10-17～18）

以下对应当前 `v1` 分支的后台任务与支付链路调整。日常操作按右侧教程进行；插件开发和已有站点更新还需核对后面的接口及结构变化。

| 变化 | 使用时需要注意 | 详细说明 |
| --- | --- | --- |
| 后台任务职责明确 | 付款准备由下单或收银台请求触发，`payment:work` 不再自动扫描并恢复付款准备；已经准备好的订单仍正常核对到账和发送通知 | [部署与后台任务](V1-18-部署与后台任务.md) |
| 单项任务异常隔离 | 单笔到期、通知或插件任务出错时按对应规则记录并处理，其他任务继续；数据库、初始化和心跳等共享故障仍明确报错 | [常见问题](V1-20-常见问题与运行排查.md) |
| 通道测试复用配置快照 | 通道“更多 → 测试”使用已经保存的配置，不为每次测试追加版本；旧订单继续使用其冻结配置 | [通道付款测试](V1-06-收款通道与支付方式.md#快速测试当前通道) |
| 回调日志直接关联流水 | 每次 HTTP 回调最多关联一条确认流水，可直接打开详情；未匹配或拒绝记录保留结果，主动采集仍支持批量逐笔确认 | [订单与到账流水](V1-09-订单与到账流水.md) |
| 订单显示支付产品与动作 | 在“处理记录 → 技术信息”查看 `pay_product`、`pay_action`，以原单实际付款准备分支为准，不猜测或补写旧记录 | [插件产品与动作](V1-23-支付插件开发.md) |
| 采集状态与通知处理精简 | 连续失败批次不等于账号重试次数，后台不推算下一次查询时间；通知保留当前尝试核验、首次有效应答和受限响应片段 | [主动采集](V1-25-主动采集与会话协作.md) · [商户通知](V1-10-商户通知与人工处理.md) |
| 合并重复校验和读取 | 通道候选与采集快照批量读取，复用本次事务或批次内已有结果；金额、归属、流水防重和交易锁内核验继续保留 | [支付链路与数据约定](V1-22-支付链路与数据约定.md) |

### 插件与后台接口变化

- 插件成功结果的付款时间统一使用 `receipt.paid_at`，外层不再重复返回 `paid_at`。产品/动作由插件按实际付款准备分支声明，字段与示例见[插件开发](V1-23-支付插件开发.md)。
- 主动采集输入移除未使用的 `current_config_version`；后台采集摘要不再提供推算的 `next_run_at`，连续失败统计使用 `consecutive_failures`，含义为连续失败批次。账号登录态、查询间隔和重试等待仍由插件维护。
- HTTP 回调日志使用单个可空的 `flow_id`，不再提供 `flow_ids`、关联流水计数及对应分页接口。二次开发的后台页面或接口调用方应同步调整。
- 单个插件配置按编码读取数据库定义，保留与本地代码的同步检查；插件列表一次统计关联通道数。配置保存复用事务中已锁定的模型，易支付单项查询复用已读支付单。
- 后台通道列表及详情不再返回未消费的 `scope_key`，详情的 `notification` 不再返回 `method`；通知地址及模式保留。内部收款范围、到账流水的范围展示与回调 POST 协议不变。这组读取精简没有数据库结构变更，不覆盖下文此前字段清理的更新边界。

### 数据库结构变化与更新边界

**本阶段包含数据库字段清理，不能沿用上一阶段“未变更数据库结构”的更新说明。** 没有新增业务表；当前结构为 25 张业务表及 1 张安装进度表，共 293 个字段。删除项如下：

| 表 | 删除字段 | 仍保留的内容 |
| --- | --- | --- |
| `ma_payment_channel_revision` | `snapshot_digest` | 冻结快照正文、配置版本及订单关联 |
| `ma_notify_task` | `lease_owner` | 当前发送认领令牌、租约时间及尝试状态 |
| `ma_notify_attempt` | `response_digest` | 商户响应片段、HTTP 状态、结果及截断标记 |

完整定义见[数据库字段字典](V1-27-数据库表与字段字典.md)。新安装直接使用更新后的 `202610140100_install` 基线；**基线名称相同不代表内容和摘要未变化**，它不是对已有数据库自动执行的升级脚本。

已有站点应先备份并核对原程序版本、数据库结构及安装进度，确认目标版本提供适用的升级方案后再更新。不要只覆盖 PHP 文件，也不要手动删除字段、修改安装摘要、重跑 `/install` 或清库来绕过检查。当前公开源码未提供旧库到这一结构的通用自动升级入口；一次文档同步也不会更新已下载的安装包。

验证码与限流新增官方依赖 `topthink/think-captcha`、`topthink/think-throttle`。从源码部署时按锁文件安装依赖，不只复制 PHP 文件；完整安装包以所下载版本的实际内容为准。10 月 16 日的验证码与限流功能未变更数据库结构，不适用于上文 17～18 日的字段清理。仍只有 `payment:watch`、`payment:work` 两个守护入口。Linux 短期缓存优先已有 tmpfs，其他环境使用 `runtime/access/`；插件登录状态继续保存在 `runtime/receipt/`。部署时保持 Web/CLI 环境一致，按正常流程重启进程，详见[部署与后台任务](V1-18-部署与后台任务.md)。

此处说明当前源码变化，不表示旧版数据库可直接覆盖升级，也不表示已经下载的安装包会随在线文档自动更新。

## 更新程序

当前交付的是纯净新装基线，只用于空库安装，未提供旧开发库到该基线的升级路径。已有站点不能直接覆盖程序后执行 `system:migrate`、重跑 `/install` 或删除安装进度表来完成升级；先确认目标版本明确提供的升级说明。以下是有适用升级路径时的操作顺序。

1. 阅读目标版本明确提供的升级路径，确认适用于当前安装版本。
2. 按[备份指南](V1-19-备份恢复与域名迁移.md)保存一致备份，记录代码、锁文件、数据库与图片的对应关系。
3. 进入维护状态，停止 watch/work，保留原 `.env`、安装锁和上传文件。
4. 部署对应源码及锁定依赖；仅执行该版本明确声明的迁移，不修改已执行 SQL 摘要，也不删除旧迁移记录。
5. 检查网站、命令行环境、数据库及原待办，再恢复两个守护进程。

更新失败不能一律用旧库覆盖，因为新到账和已发送通知可能已经发生。先保全当前状态、核对副作用，再按恢复方案处理。

## 文档怎么跟随版本

README 是产品入口，`docs/wiki/` 是对外正文的唯一源文件，远程 Wiki 是发布副本。每次改接口、配置字段、默认值、状态或后台操作，应同步对应教程和示例。

在线 Wiki 跟随 V1 当前源码更新。使用较早版本时，应阅读与程序对应版本的文档，避免把新界面的按钮或插件接口直接套到旧程序上：

- 源码包保留 `docs/wiki/`，可直接离线阅读同版本正文和图片。
- 纯净安装包不含 `docs/`，先阅读包内 README；再依据下载时记录的版本或源码提交号，在源码仓库选择对应版本查看 `docs/wiki/`，不要默认最新 Wiki 适用于旧包。

两端源码入口为 [Gitee v1](https://gitee.com/technical-laohu/mpay/tree/v1/) 和 [GitHub v1](https://github.com/techhaha/mpay/tree/v1)，当前默认分支均为 `v1`；查看历史链接或下载旧包时仍须核对版本。源码与远程 Wiki 分别保存 Git 历史，文档已更新不代表站点程序或已下载的安装包也已更新。

文档截图使用当前界面和明确的演示数据，不把截图中的金额/状态作为真实平台已验收的证据。接口示例不用真实 KEY 或账号；未知的平台版本明确写明待核对，不补造“通用规则”。

开发者可运行 `python docs/wiki/tools/wiki.py check` 检查本地链接和图片。同步工具的使用见[发布工具说明](tools/README.md)；默认只检查，写出发布目录需要显式参数，工具本身不提交或推送 Git。
