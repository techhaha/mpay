# 业务边界与回归验收

维护目标是让业务入口、交易保护和失败处理容易理解、能够验证。代码行数、类数量和 SQL 次数是观察指标，不能单独作为修改理由。

## 完整业务入口

下表中的入口承担一个完整业务操作。Controller 先完成 HTTP 验证、会话和 CSRF 等适用检查，再调用对应入口；CLI 也必须使用相应的受信任上下文。

| 操作 | 业务入口 | 内部协作与事务边界 |
| --- | --- | --- |
| 易支付下单 | EpayV1ProtocolService → PayOrderService::create | 协议层认证与归一化；建单事务核对应用、凭证版本、指纹和选路，提交后派发插件 |
| 后台指定通道测试 | PaymentChannelTestService::create | 在管理员授权事务内调用 createLocked，复用正式订单规则 |
| 收银台查询、选择方式、准备材料 | CashierService | 先核对订单访问凭证并限流；选方式与派发保留各自锁内核验，网络后重新读取展示 |
| 收银台默认成功页 | CashierService::successPage | 一个只读事务核验凭证、双单关联/状态、原金额及商户首次 ACK；模板只取所需字段，读取限流计一次 |
| 通道新增、编辑、参数保存、启停、删除 | PaymentChannelEditorService | 统一管理员授权、版本和接入判断、锁序；参数及通道子服务在同一事务内协作 |
| 设备/平台通知 | PayOrderCallbackService::receiveChannel | 通道 ID 使用当前配置，支付单号使用冻结配置；插件认证解析，服务复核后由生命周期事务确认 |
| 主动采集 | ReceiptWatcherService::runRound | collect 交付订单和通道版本；采集结果按通道初始化后调用 notify，插件自行查询匹配订单，列表经回调服务逐笔确认 |
| 人工确认、关闭、通知补发 | PayOrderAdminActionService | 确认前复核密码；管理员版本、原单状态及通知责任在对应事务内核验 |
| 退款 | 已认证易支付入口 → RefundService::refund | 原订单锁内核对归属与退款额度；外部动作在事务外，未知结果不自动重发 |
| 商户通知 | MerchantNotifyDispatcherService::dispatchOne | 认领和回写分别为短事务；HTTP 在事务外，回写核对当前令牌和尝试 |
| 订单到期 | PaymentRuntimeMaintenanceService → PayOrderLifecycleService::expire | 逐笔锁内判断到期，单笔异常隔离；不自动准备付款 |

`PaymentPluginConfService`、`PaymentChannelService` 和 `PayOrderAttemptService` 是内部协作服务。普通入口不能跳过上表的完整用例，直接调用这些子服务。`createLocked` 只用于已约定的组合事务；`ReceiptEvent` 由回调服务在标准结果验证后构造，插件继续返回标准数组。

`@internal` 与 `InTransaction` 命名说明调用约定，不是 PHP 的访问控制或运行时安全证明。`requireTransaction()` 只能确认连接处于事务中，不能证明调用者已鉴权、传入模型已加锁或版本已核对。新增调用方时必须逐项核对这些前提，不添加 skipValidation、任意 CRUD 或绕过入口的快捷分支。

## 数据和交易保护

- 输入格式由入口验证器负责；平台来源认证由插件或 SDK 负责；金额、归属和状态由服务负责。相似条件处在不同信任或并发边界时应保留。
- 同一事务内可以复用刚读到、没有发生失效的结果。跨事务、等待锁或外部请求后的状态，必须重新核对；不得把旧模型当作最新交易事实。
- 金额使用整数分；业务单和支付单关联、实际收款金额、付款窗口、流水身份与通知责任不能因优化而删减。
- 唯一索引、锁序、条件更新、执行令牌和首次有效 ACK 各有职责。单条接口成功、二维码生成和浏览器回跳均不证明到账。
- 同单重投采用冻结参数和有效期；当前默认有效期只用于新建业务单。完整收银台读取额外核对金额，轻量轮询只读取所需状态字段。
- 保留业务含义清晰的类型、必要的异常隔离与诊断。不能为少一次对象转换、少几行代码而修改多个层的合同。

## 插件扩展边界

`payment/` 只放插件主类，`interface/` 与 `sdk/` 保持独立。插件声明 config_schema、解释平台账号、管理认证状态和匹配流水；SDK 封装平台 HTTP、签名和解析；公共服务校验标准结果并统一提交交易。

公共服务不猜账号字段、不解释第三方错误码，也不把核心 ORM 模型、事务控制或内部到账对象加入插件接口。相似代码是否抽取，取决于规则是否稳定一致；BasePayment 仅复用配置保存及元信息读取，不抽取支付、平台 HTTP 或匹配逻辑。

插件单项读取使用已同步映射并核对固定目录、接口和实际编码，不为找一个插件装配全目录；完整目录刷新仍检查编码唯一性。原单配置的共同结构和归属核验集中在既有通道版本服务，各动作的权限、金额、状态及锁内复核不迁入该读取方法。它不补活动配置、不校验 schema 值、不比较当前代码版本。

epay API 插件实现统一 PaymentInterface，notify 处理 HTTP 并返回一项结果列表，不参加主动采集。普通订单确认走 `confirmPayment`，带流水结果仍走 `confirmReceipt`；两者都只供已认证的公共回调编排使用，不暴露为匿名成功接口。前者核对冻结配置、方式、金额、原平台单号和状态，后者继续核对匹配事实及流水防重。平台同单重报不新增商户通知；不同站点的平台订单号允许相同。源码装配和语法检查不能替代真实平台下单、回调及退款验收。

## 关键回归清单

以下是验收要求，不表示这些场景已经在某一版本通过。每次只选择本次变更直接涉及的场景，再补足其必要失败分支；记录实际结果和未覆盖项。

| 编号 | 操作与扰动 | 必须观察的结果 |
| --- | --- | --- |
| T01 | 同应用、同外部单号、同参数重复下单 | 原业务单、支付单、通道和令牌复用；不多推进轮询游标 |
| T02 | 同号修改金额、通知目标或指定通道 | 明确拒绝，原订单内容不变；另一应用的同号独立处理 |
| T03 | 错误订单访问令牌、跨应用查单、损坏双单关联 | 拒绝访问或明确报错，不能返回另一笔订单的付款材料 |
| T04 | 默认有效期改变后重投旧单；再创建新单 | 旧单期限和指纹保持；新单使用当前合法默认值 |
| T05 | 过期配置版本或失效管理员修改、启停通道 | 事务内拒绝，配置、快照及审计无半完成写入 |
| T06 | 两个连接同时下单与编辑通道，或同时分配同通道识别金额 | 保持既定锁序和金额/备注规则，不出现重复尝试或交叉归属 |
| T07 | 相同流水重报、同键不同金额或付款时间、企图绑定另一订单 | 重报幂等；冲突拒绝；成功事实与原流水绑定保持 |
| T08 | 付款窗口内的迟到消息、窗口外的旧流水 | 按原单窗口核对，旧到账不分配给新单 |
| T09 | 两个请求同时准备付款，或认领后进程中断 | 同一有效认领不并发调用插件；租约到期由普通请求按原单恢复，原识别事实不变 |
| T10 | 已成功后旧准备结果回写；未知结果重试 | 旧令牌/过期结果不覆盖成功；不能把未知改为确定失败并换通道重付 |
| T11 | 人工确认密码错误、证据不足、重报或试图覆盖成功事实 | 分别拒绝或幂等；实收、付款时间、交易号及通知安排保持一致 |
| T12 | POST /api.php?act=refund、GET 退款拒绝、退款成功、准备失败、插件不支持、上游明确拒绝、动作后网络未知、相同退款号重投及入口参数/认证/限流/程序异常 | 插件 act 位于 URL；GET 退款为 HTTP 405/Allow: POST/code=-1 且不调用退款服务；仅明确成功 code=0，其余为 -1；内部状态不变，准备失败不冒充已执行，拒绝和未知均有受限脱敏诊断，未知保留额度和原请求，不自动二次退款 |
| T13 | 通知租约过期，新进程认领后旧进程返回 ACK | 旧结果不覆盖新尝试；当前任务与尝试一致 |
| T14 | 首次有效 ACK 后人工补发失败；商户返回超长或错误正文 | 首次确认保持；受限正文、截断标记与错误原因可查 |
| T15 | 采集响应夹带调度范围外旧流水、跨通道歧义、账号认证失败、单笔确认或到期异常 | 只比对本轮候选，歧义跳过；逐笔失败不计成功且不阻断其他确认，共享数据库故障明确上抛 |
| T16 | 插件配置无描述、秘密字段、条件字段、未知声明 | 按插件 schema 如实渲染并验证；系统不添加平台业务字段或使用说明 |
| T17 | 新装库、旧迁移链、损坏摘要、安装中断后继续 | 正确区分原因；旧库和损坏记录拒绝接管，不靠改摘要跳过保护 |
| T18 | 商户确认等待期间隐藏页面，超时后恢复；补查时仍有请求或限流等待；直接访问成功页 | 恢复时只补查一次完成状态，不重启 60 秒等待、不补发通知；满足付款与商户确认才导航；成功页在一个事务内授权、核对双单和金额并读取模板字段，不重复计算读取额度 |
| T19 | 单项读取插件、目标映射缺失或指向目录外/编码不符；全量刷新遇到重复编码 | 普通单项不实例化其他插件，目标异常明确拒绝且不回退扫描；全量刷新仍拒绝重复编码，停用插件仍可读取配置修正 |
| T20 | 原单通道快照结构或归属损坏、配置修改及代码版本变化；查询单笔与列表 | 付款、支付号回调和退款使用一致的冻结核验，不回退当前参数，不以当前代码版本挡旧单；原金额、锁内状态和退款未执行分类保持；查询只在外层返回 code/msg，关联损坏仍拒绝 |
| T21 | 三家银行入账、支出、普通消息、错来源/卡尾、畸形消息游标、分钟精度时间、旧消息、缺失或无效交易时间、金额歧义及重复通知 | 仅既定人民币入账唯一匹配才确认；明确非入账返回空列表正常 ACK，实际入账匹配失败抛错；游标非标量按格式错误拒绝；窗口取实际精度和原微信时间约束，不以请求时间替代；事件键稳定且交易号为空，旧消息不改绑，业务金额与实际入账分别保存 |
| T21 | 关闭等待事务锁、重复关闭；认领/回写时订单已到期；维护扫描后订单成功；关闭/超时后收到原窗口内可信到账 | 关闭时间取必要锁后的 Clock，双单共用且重报不改原时间；内部到期复用已锁定核验的支付单，独立维护入口仍完整加锁复核；成功不降级，可信迟到到账仍按原证据处理，原窗口及快照保留 |

验收记录至少包含程序提交号或差异摘要、目标环境、数据库与隔离方式、步骤、预期和实际结果。只记录脱敏编号与证据，不保存真实凭证或完整平台报文到公开文档。

单连接 TEMPORARY 表可验证业务分支和唯一索引；移除外键的临时表不能证明外键正确，多次顺序执行也不能证明并发安全。T06、T09、T13 的竞争部分需要独立连接或进程，并验证它们确实发生交叠。平台响应替身只能验证本地处理，真实登录、查单和资金操作需单独标明实际范围。

### 并发和中断的验收方法

- 并发下单使用独立数据库连接，同时提交同应用、同外部单号；通过 InnoDB 等待关系确认发生锁竞争，再核对业务单、支付单、访问令牌及轮询游标。同号金额冲突应只接受一笔。同通道两笔原金额相同的订单同时准备付款，识别金额不能重复。
- 付款准备分别在“认领已提交、尚未调用插件”和“插件已保存识别信息、尚未回写展示结果”中断进程。等待真实租约到期，由普通准备请求触发安全恢复，核对原识别信息、首次发起时间、付款窗口和支付单保持。恢复时仍使用原支付号；本地认领验证不能证明第三方重复请求一定幂等，不能据此宣称真实外部支付产品已通过验收。
- 通知测试让旧进程收到 HTTP ACK 后暂停，等待真实租约到期，再由另一个进程接管。分别在新尝试发送中和新尝试成功之后恢复旧进程，旧回写应返回 `lease_lost`，不得修改当前任务、尝试记录或首次 ACK。接收器位于本机时，只能证明本地 HTTP 与持久化链路，不能替代真实商户的网络和履约验收。

独立验收库使用正式建表定义，保留外键和唯一索引；不能为了制造并发关闭交易保护。结束后核对原业务数据，并清理独立验收库、进程和缓存。执行细节和通过记录保存在维护资料，不把清单中的全部项目笼统标为通过。

根目录诊断工具按项目规则仅在本地保留。清单不要求引入新的测试框架；具体可执行命令必须与当前环境实际存在的工具一致，不能把历史记录当作本轮通过。

## 修改与发布原则

一次修改围绕一个明确问题，说明原行为、目标行为、维护收益、合同变化及验证范围。复用数据前先定位其产生和失效边界，不为减少查询让更多层依赖可变模型或隐含调用顺序。

开发阶段的结构清理须明确目标库、备份、实际结构和账本来源；核验已有库与新装结构接近，不代表它具有新装历史。当前安装器只支持其固定新装基线，不自动接管旧迁移链。不能改摘要、删账本或清空业务库来掩盖版本不匹配。

客户稳定版本发布后，已发布的安装定义应固定；后续数据库变化需提供对应版本的升级步骤、备份要求、失败恢复办法和验收结果。新安装与已有站点升级分别说明。此处是发布要求，不表示当前版本已提供通用升级执行器。
