# 银行卡公众号收款

银行卡收款通过微信监听工具接收银行公众号的完整动账消息，不调用银行支付 API。付款人按收银台显示的银行、户名、卡号和应付金额自行转账；插件核对入账通知并匹配订单，系统再确认收款、保存最终到账流水并通知业务网站。

## 支持的银行与消息

| 插件 | 编码 | 固定公众号 | 入账范围 |
| --- | --- | --- | --- |
| 中国银行银行卡收款 | bank_of_china_receipt | 中国银行微银行 gh_19b52c2473d6 | “交易成功提醒”中的人民币银联入账、网上快捷提现入账 |
| 中国建设银行银行卡收款 | china_construction_bank_receipt | 中国建设银行 gh_a19f4d5e89e5 | “交易提醒”中的人民币储蓄账户收入 |
| 中国工商银行银行卡收款 | icbc_receipt | 中国工商银行客户服务 gh_6be1b2174d18 | “动账交易提醒”中的借记卡人民币银联入账 |

公众号身份由插件固定声明，不需要填写。只接受以上已有格式，其他银行和未识别交易类型不自动确认。微信消息方向为 incoming 只说明收到了公众号消息，银行卡资金方向还要根据银行正文判断。

中国银行的交易类型仅接受 `银联入账（尾号四位数字）` 和 `网上快捷提现（尾号四位数字）` 两种完整格式，二者共用卡尾、人民币金额、交易时间、原订单窗口及唯一订单校验；不会仅凭正文包含“提现”就确认收款。“二维码消费”消息仍忽略，其他未知交易类型继续拒绝。

三个独立插件各自解释银行模板和时间格式；BankReceiptMessage 只共享消息结构、XML、字段、金额和基础日期转换，不包含中行、建行或工行的专用规则。中行无年份交易时间的补全留在中行插件内部，建行和工行的日期格式也分别由自己的插件处理。

## 启用与配置

1. 新安装会建立编码 `bank`、名称“银行卡转账”的支付方式，并将蓝色银行卡小图标和完整标识作为图片资产保存到支付方式配置。已有安装若没有该方式，在“插件管理 → 支付方式”新增，保持编码为 `bank`，通过“选择图片”分别设置小图标与完整标识；未设置时显示通用收款图标；系统会按现有规则维护默认轮询组及默认模式应用的绑定。`bank` 与云闪付 `unionpay` 是两种不同方式。
2. 在“插件管理”刷新插件定义，并启用对应的银行插件。
3. 在“收款配置”新增通道，选择“银行卡转账”和对应银行插件，填写通用限额及下表参数，最后保存并启用。
4. 为微信监听工具中对应公众号单独配置通知目标和通知密钥。使用通道详情提供的接入地址，不把登录资料或通知密钥填到付款页面。
5. 业务网站使用本站应用 PID/KEY 下单，指定 `type=bank`；页面下单也可省略支付方式，由付款人选择。应用必须有可用的银行卡路由。

| 参数 | 配置字段 | 规则 |
| --- | --- | --- |
| 收款户名 | account_name | 必填，1～100 个字符，不含控制字符 |
| 收款银行卡号 | card_number | 必填，12～19 位数字，可用空格或短横线分组 |
| 付款有效期 | receipt_valid_seconds | 60～1800 秒，默认 300 秒，不超过原订单截止时间 |
| 金额偏移上限 | amount_offset_max | 0～99 分，默认 99 分；0 表示不增加金额 |
| 通知密钥 | sms_forwarder_secret | 6～32 个字符，与通知工具保持一致 |
| 通知时间容差 | sms_forwarder_time_tolerance | 5～30 秒，默认 30 秒，比较本次请求时间与服务器时间 |

银行卡通知没有付款备注，插件固定按金额匹配，不提供备注模式或收款码上传。说明、默认值和校验均由各插件 config_schema 声明，系统不会额外注入配置字段。银行卡号和户名是付款人需要看到的公开收款资料，通知密钥仍只用于后台配置和来源认证。

卡号的 12～19 位及分组格式在保存、启用时按 schema 校验。运行时只去掉空格和短横线，用于收银台展示及消息卡尾核对；不会再次检查同一配置的卡号格式。入账消息的来源、卡尾、币种、金额和时间校验仍分别执行。

同一张卡建议只配置一个通道，多应用可以共用该通道。系统允许保存重复账号配置，但金额唯一性只在单个通道内成立；卡尾四位也不能证明完整卡号，同卡多通道不具备自动消除跨通道歧义的能力。

## 付款与金额

插件在业务单、支付单、通道的既定锁序内，从当前通道尚未占用的金额中分配识别值。例如原订单均为 10.00 元，两笔订单可能分别显示 10.00 元和 10.01 元。付款人必须按自己的页面金额精确转账，不需要填写付款备注。

识别准备沿用 V1 数据合同：等待付款时 pay_amount 可以包含识别偏移，personal_receipt 保存 original_amount、receipt_amount、match_mode=amount 和 remark=null。同一原单重复打开复用金额和期限，不重新分配、不延长付款时间。成功后生命周期恢复业务金额，实际入账金额保留在最终到账流水和原单收款证据中。

标准成功结果的 paid_amount 是原业务金额，receipt.amount 是实际入账金额。例如原订单 10.00 元、实际转账 10.01 元，对应 1000 分和 1001 分；商户通知仍使用原订单 10.00 元。插件不自行写成功状态、生成通知或提前保存流水。

收银台使用 page/bankTransfer 展示，公开参数只有 bank_name、account_name、card_number。应付金额和倒计时读取公共 amount、expires_at、server_time，不在插件页面参数中再保存一份金额或期限。户名、卡号和应付金额可复制；到期、关闭及成功后移除付款资料，后续查询和商户回跳共用现有收银台流程。本地关闭不能阻止银行卡继续收到转账。

## 通知格式与确认

通知使用现有 POST `/api/pay/{通道ID}/notify`，表单字段为 from、content、timestamp、sign。from 为该银行固定公众号标识；content 为完整的 wxtool.officialAccount.message JSON 事件，不是通知摘要；timestamp 为本次投递的 13 位毫秒时间戳。sign 沿用监听表单 HMAC-SHA256 约定，计算内容为 timestamp、换行及通知密钥，HMAC 密钥也是该通知密钥，表单按正常规则编码发送。

沿用的签名只认证请求时间戳，不能据此宣称银行正文由银行官方签名。监听工具及其运行环境应可信。公共字段、签名和来源由既有 SmsForwarderValidator 检查，银行插件继续检查完整事件、发送方、微信消息游标和银行入账内容。

事件需要 account.username 以及 message.username/source/isFallback/direction/senderUsername/localType/createTime/content。银行 appmsg 的 localType 为整数 21474836529。delivery.messageKey 必须由原微信账号标识、公众号、sortSeq、createTime、localId 五段组成，并与原消息一致；sortSeq、localId 只接受整数或与消息键一致的数字字符串，数组等类型按消息格式错误拒绝。XML 只接受唯一的 appmsg/title 与 appmsg/des，正文中的银行字段不允许空值或重复。沿用公共入口 URL 与正文合计 64 KiB、监听 content 最多 32 KiB 的限制，不扩大到 V2 的 2 MiB。

各银行仅识别既定的人民币入账格式，并核对卡尾四位、整数分金额、原订单识别窗口和唯一候选。明确的发出消息、普通文本、无关标题以及已识别的消费/支出消息正常忽略，不生成流水、不改变订单。已识别交易标题下的未知交易格式、错签名、错公众号、错卡尾、实际入账无匹配或匹配多笔时拒绝并记录现有诊断信息。

## 交易时间与重复通知

中国银行的交易时间没有年份，按微信原消息时间选择最近的相邻年份。中行和工行部分时间只精确到分钟，按该分钟区间与原订单窗口求交，不把它伪装为精确到秒；建行时间按包含年份和秒的格式解析。只有交易时间字段完全缺失时才使用微信消息 createTime，出现但为空、重复、日期无效或格式未知时拒绝，不回退成本次请求时间。

银行时间不得晚于微信消息时间，两者最多相差 300 秒。候选窗口使用区间交集：原订单识别开始不晚于银行时间区间终点与微信消息时间的较早者，订单截止严格晚于银行时间下界；因此微信消息也必须早于订单截止后 300 秒，不包含截止后的第 300 秒边界。这是银行消息与原付款窗口的核对规则，与默认 30 秒的 HTTP 通知时间容差分别处理。分钟精度造成多个原订单都可能匹配时仍拒绝，不选择其中一笔猜测确认。

银行通知没有提供可核验的官方流水号，因此 receipt.trade_no、chan_trade_no、chan_order_no 都为 null。事件键使用 `BR` 加原 messageKey 的 SHA-256 摘要，不包含通道 ID、投递时间或重试次数。同一消息重投键不变；同插件跨通道投递仍受现有事件唯一约束保护，不会重复确认两笔订单，但不能代替正确的通道配置与订单定位。

已匹配消息重投会核对原订单识别金额及窗口，再走现有幂等确认；同键不同入账金额或付款时间拒绝，不能改绑另一订单。事件摘要针对标准收款事实，不承诺逐字比较原始 XML 或余额等无关字段。付款时间只通过 receipt.paid_at 提供。数据库仅保存最终匹配的到账流水，消息正文、余额、完整卡号及未匹配收款不进入流水记录；回调日志沿用摘要和可空 flow_id，技术错误不附带原始银行正文或密钥。

## 应答与排查

已确认或明确忽略的消息返回字符串 `200`；业务拒绝返回 `400：错误原因`，框架默认 HTTP 200。程序或数据库故障仍由统一异常处理，不伪装成正常忽略。监听工具成功关键字填 `200`，不要与业务网站确认商户通知时返回的 `success` 混用。

后台可通过“通道回调日志”查看接收结果及请求编号，实际确认成功后再在订单及到账流水查看绑定事实。若不能匹配，先核对银行插件、公众号来源、当前卡尾、页面应付金额和原单窗口，再按请求编号检查脱敏技术日志。

插件没有银行 API 查单或接口退款能力，不需要增加采集任务、预登录或新的守护入口。银行消息格式变化需要更新对应插件解析，付款和商户通知继续使用公共流程。
